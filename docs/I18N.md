# Languages (I18N)

OpenVireo is in English and, since Front ES-REL (2026-11-09), in Spanish (es-419): a browser whose first language is any `es-*`
opens Spanish, every other browser English, and the English / Español selector changes it (user decisions of 2026-11-09,
AGENTS.md; plan `analysis/front-plans/front-i18n-es.md` in the research root; the release is the last section of this file).
This file describes the infrastructure of Front ES0, the shell slice of Front ES1, the observatory of Front ES2, the exercise
fronts ES3–ES9, the help files (ES-HELP), the chunk split (ES-SPLIT) and the release (ES-REL), in the order they were built.
The status lines of each front describe the tree when it merged. Until ES-REL Spanish was hidden (decision 5): only a
`?lang=es-419` preview link showed it, and from ES1 that preview had the whole shell in Spanish (header, menu, home, toolbar, tour, Help menu web text, project links, error and recovery
texts, instructor mode, `document.title`) and a language selector. From ES2 the optical observatory was Spanish too, from ES3 the whole E01 flow, and so on front by front until every screen was.

## What a translation is

- Translations are **web adaptations by OpenVireo**. They never claim to be CLEA's.
- CLEA's original bytes, hashes, manifests and provenance do not change.
- **Files the site writes stay English** and byte-identical in every language (decision 3). This covers TXT, FITS, CSV,
  HTL, PLR, saved investigations, sessions, options files and every other export.
- **Text on screen that mirrors a written file** (a native list window, a results preview) stays English, with a caption in
  the screen language (decision 9, F2 below).
- **Numbers keep the decimal point** on screen in every language, as typed inputs and files do (decision 4).
- The Spanish addresses the student as **tú** (decision 6).

## The language of one load

The language is settled once per page load, in `src/boot.ts`, which `src/main.tsx` imports first. `index.html` and the entry
are unchanged. Boot calls `settleLanguage` (`src/i18n/settle.ts`, unit-tested with a stand-in page):

1. **Decide** (`src/i18n/locale.ts`, `decideLocale`, a pure function):
   1. a `?lang=` link parameter: `en` or `es-419` (`qps` only in the dev server). It applies to that load and is not stored;
   2. the stored choice: localStorage `openvireo-language`, read in a try/catch;
   3. the browser language: the first entry of `navigator.languages` decides; `es`, `es-MX`, `es-ES`… give es-419, and
      everything else gives English.
2. **Release gate (decision 5).** Until ES-REL, `SPANISH_RELEASED` was `false`: steps 2 and 3 were skipped, so only an explicit
   `?lang=es-419` preview link asked for Spanish. Since ES-REL it is `true`.
3. **Bundle.** English needs none, and the dev-only pseudo-locale is built synchronously from the English sources. Spanish is
   its own chunk, `src/i18n/es/index.ts`, imported dynamically only for a Spanish load (see "How the Spanish bundle arrives").
4. **View original (English)** (decision 9): when localStorage `openvireo-vireo-originals` is `1`, the bundle's VIREO
   originals are dropped, so `vireo()` returns VIREO's exact texts while OpenVireo's own text stays translated. Read at load.
5. **Activate** it (`activateLocale`), set `<html lang>`, and, for a non-English load, `document.title`. A bundle that cannot
   be built or does not validate (a wrong catalog, an unknown map id) is logged and replaced by English, so a broken
   translation never blanks the page.

**No text is read when a module evaluates.** The production build evaluates the shared chunks that the entry chunk imports
*before* the entry chunk's own code (Rolldown), and a Spanish load evaluates every app module before its chunk is active. So
no module may read text when it evaluates:
- every `pickMessages` map, and the catalog-backed `CLUSTER_NATIVE_HR_MESSAGES`, is a `lazyMessages` view
  (`src/i18n/registry.ts`) built on first read. Since ES1 a read of a nested part or a function (`const M=X.entry`,
  `const f=X.format`) returns a view of that part or a function that builds when called, so module-level aliases stay lazy;
- module-level translators are made on their first call (`lazyTranslator`);
- module-level tables of text are built on first read (`lazyMessages(()=>({…}))`) or read through getters. ES1 converted the
  last ones: the target catalog labels and groups in `OpenVireo.tsx`, `SESSION_HINTS` and `SESSION_NOTES` in
  `OpticalOptionsDialog.tsx`, the Sky and Star exposure session notices, the reference titles in `SpectrumInstrument.tsx`,
  the Radio Save texts and translators in `RadioReceiverWindows.tsx` and `RadioControlPanel.tsx`, and two Object X aliases;
- `t` and `vireo()` read the active language when they are called.

`src/i18n/moduleEvaluation.test.ts` imports every source module with no language settled and fails on any text read.

**Guard.** In the dev server and in Vitest, asking for text before the language is settled throws (the tripwire). In
production the request is answered in English and counted (`earlyTextRequests`), and boot logs a console error with the
count; the active-language holder is set only by `activateLocale` (and, since ES-SPLIT, by `extendLocale` and
`markAreaFailed` for a route area's text). `tests/release/pages-smoke.pages.ts` opens every route of the production build and
a `?lang=es-419` preview, and requires that the holder is activated once, then extended once per route area loaded (same
language), never read while empty, and that no console error appears. The holder lives on `globalThis` (`Symbol.for('openvireo.i18n.active')`), so a
re-evaluated copy of the module (a hot update, `vi.resetModules`) keeps the language.

`src/boot.ts` statically imports only the catalog machinery (`src/i18n/catalog.ts`, `active.ts`, `locale.ts`, `maps.ts`,
`settle.ts`) and `pseudo.ts`, which the production build drops with its `import.meta.env.DEV` branch. `src/i18n/index.ts`
re-exports them with `t`. Entries that do not go through `main.tsx` import `src/i18n/useEnglish.ts` first: the Vitest setup
(`vite.config.ts`) and the standalone test harnesses under `tests/harness/`.

### How the Spanish bundle arrives (ES0 measurements, ES1 decision)

The plan made `src/boot.ts` the page entry, loaded the Spanish bundle lazily and then ran `await import('./main')`, with a
Vite plugin that preloads the app chunk in `index.html`. That was built and measured, and it changed three things:
- **The window load event** no longer waited for the app: a dynamic import does not delay it. Tests that act right after
  `page.goto()` (for example `focus-after-layout.spec.ts` and `cluster-native-observation-hr.spec.ts`) failed, because
  `goto()` returned before the app had evaluated. A top-level await in the entry does not delay the load event either.
- **Rolldown's chunks** changed: with the app as a dynamic entry, six small shared chunks appeared and five disappeared,
  and the app's CSS came out in another module order (`help.css` became its own file; `hubble-lab.css`,
  `spectrum-engine.css` and `help.css` moved before the base styles). The computed styles of every element were compared on
  twelve routes and six menu and phone states, with no difference, but the order was no longer Vite's own.
- **Size:** +3.2 KB gzip on the files `index.html` loads (+2.2 KB raw), mostly chunk overhead.

A top-level await in the catalog module, to keep `main.tsx` as the entry, split the entry far more (+13.6 KB gzip). The
reviewer measured `build.rolldownOptions.output.strictExecutionOrder: true` at +22.3 KB gzip and +20.2 KB brotli, with eight
more files.

**ES1 decision: option (c).** Boot stays synchronous. For English (and qps) the language is active before `main.tsx`
renders, exactly as before. For Spanish, `settleLanguage` returns a promise: boot imports `src/i18n/es/index.ts`, activates it
(or English, logging the failure), and `main.tsx` calls `createRoot(...).render(...)` only when that promise settles. Because
no module reads text when it evaluates, no text is read before activation. The chunk races a 10 s timeout
(`LANGUAGE_TIMEOUT_MS`); whichever settles first decides once, so a chunk that arrives later is never activated. When the
chunk fails, times out or does not validate, the page renders in English and shows a one-line notice in both languages
(`LANGUAGE_FAILURE_NOTICE`, `src/i18n/active.ts`: its own small text, since the Spanish catalog is what failed); settle
returns `{language, failed}`. Measured on the production build:
- the release smoke (`tests/release/pages-smoke.pages.ts`) and a preview probe show the language holder set once and never
  read empty, in English and in Spanish;
- English loads never request the Spanish chunk or the language selector;
- the English entry, chunks and stylesheets are those of fab442e except the additions listed under "Loading cost";
- a Spanish load's window `load` event no longer waits for the app's first render (the chunk is awaited after it); the
  English suite is unaffected, and the Spanish specs wait for the page's own heading.

**Loading cost.** Measured with `npm run build` on the files `index.html` loads (gzip and brotli per file):

| | files | raw | gzip | brotli |
|---|---|---|---|---|
| main 033f693 (before ES0) | 77 | 4,005,050 | 1,011,899 | 740,546 |
| fab442e (ES0) | 76 | 4,009,239 | 1,013,702 | 742,340 |
| ES1 (with review 1) | 76 | 4,013,295 (+4,056) | 1,015,201 (+1,499) | 743,592 (+1,252) |

Against fab442e, three files grow: the entry (`index`: the Spanish chunk's import stub with its timeout, the deferred
render, the failure notice, the lazy selector stub and the module-level conversions), the shared chunk that holds the i18n
machinery (lazy views, `lazyTranslator`, partial-map completion, the new map ids) and the main stylesheet (+192 B, the
review-1 header layout fix of C5, which applies to English too). `index.html` lists the same files (one preload moved); every
other CSS file is byte-identical. The Spanish chunk is 22,375 B (7,537 gzip, 6,685 brotli); the selector, loaded only when
shown, is 4,131 B (1,705 gzip) plus its own 492-byte stylesheet.

## The language selector (ES1)

`src/components/LanguageChoice.tsx`, lazily loaded at the foot of the header menu beside the theme switch. Its texts are the map
`languageChoice` (`src/components/LanguageChoiceMessages.ts`), outside en.json, so they arrive with the selector's own chunk (before
ES-REL only preview loads fetched it; since ES-REL every load does, after the first render).
- **Shown** (`selectorShown`, `src/i18n/locale.ts`): since ES-REL on every load (English loads fetch its small chunk too); before it
  only on a load whose address had `?lang=en` or `?lang=es-419` exactly (the preview), so the reload flow could be tested.
- **English / Español** radio buttons, each named in its own language under the bilingual legend "Idioma / Language".
- **Changing** opens a confirmation in the current language. It says the page reloads on the same page and what that keeps
  and loses, checked against what the app persists:
  - lost: everything only on screen (pointing, running exposures, measurements, open windows, instructor mode, anything not
    saved to a file);
  - kept: files the visitor saved (Restore investigation JSON loads them again), and in this browser the confirmed
    observation results (`openvireo.observation-notebook.v1`) and display preferences (theme, menu sections, the tour, the ?
    key, Demonstration Mode).

  Buttons: Save investigation (the toolbar's save, which downloads the investigation first), Change and reload, Cancel
  (also Escape). Before ES-REL the choice was **never stored** (user decision in ES1 review 1, C2): the preview language came
  only from `?lang=`, so a tester's choice could not start applying after the release. Since ES-REL the choice is stored
  (try/catch) and the page reloads at the same address; when storage fails, or the address already has `?lang=`, the choice is
  carried as `?lang=` too, and a failed store is said in the dialog (it is not remembered). The #route is kept.
- **View original (English)**: a checkbox stored in `openvireo-vireo-originals`, applied at the next load (decision 9). In
  ES1 it changes only the vireo() sites already translated (the Help menu captions and Results Editors); more come with ES2.

## Three kinds of text

| Source | How it is translated | Where the translation lives (from ES1) |
|---|---|---|
| `src/i18n/en.json` (`t`) | `t` delegates to the active catalog; missing keys fell back to English until ES-REL (since then the catalog is complete; a split module still builds with the fallback) | `src/i18n/es/es.json` |
| The 26 `*Messages.ts` files, `help/tour.ts` and `help/projectLinks.ts` (31 maps) | `export const X=pickMessages('id',X_EN)`, built on first read; the 6 flat translators default to `pickMessages('id',X_EN)` | `src/i18n/es/maps/<id>.ts`, typed `Translation<typeof X_EN>`, or `PartialTranslation` before ES-REL (`BundleMaps`, `src/i18n/maps.ts`) |
| VIREO's own literals in `src/core/` | opt-in at each render site: `vireo(LITERAL)` | `src/i18n/es/originals.json`, keyed by the normalised original |

**`*Messages.ts` maps.** Consumers read the picked name (`CAMERA_MESSAGES`, `CLUSTER_HR`, `OBJECT_X_LAB`, …). The `_EN` name
is the typed English source; tests and the Spanish maps use it. In English, every picked map reads the English map's values.
- Before ES-REL a Spanish map could be partial: `resolveMessages` checked it with `mapParity(…,{partial:true})` and completed the
  missing strings with English (`completeWithEnglish`, `src/i18n/parity.ts`), as the catalog's fallback mode does. Since ES-REL a
  Spanish map must be complete (a partial one stays English and is logged in production; `es.test.ts` fails on it).
- The tour's text and the project links' text are maps since ES1 (`TOUR_EN`, `PROJECT_LINKS_EN`); the tour's targets and the
  English issue template (`ISSUE_TEMPLATE`, F5) are not text and stay outside them.
- `src/i18n/maps.ts` lists the 31 ids (`MAP_IDS`) and types a bundle's maps by id (`BundleMaps`). `activateLocale` refuses a
  bundle with an unknown map id.
- On first read, `resolveMessages` checks the bundle's map against the English map with `mapParity`
  (`src/i18n/parity.ts`): the same keys at every depth, the same kind, the same `{param}` set and the same function arity.
  A mismatch throws in the dev server and tests; in production that map stays English and the problem is logged.
- Two maps are **catalog-backed** and therefore not registered: `CLUSTER_NATIVE_HR_MESSAGES` (every value is a `t()` call,
  built lazily) and `RADIO_MESSAGES_EN` (its translator renders through `t`). Their Spanish comes with en.json, so coverage
  does not count them twice and qps marks them once.
- Each id is picked in exactly one source line (`infrastructure.test.ts`).
- Known limit: the dev pseudo-locale also marks map leaves that are not display text, if a map holds any; such a leaf would
  show up as a marked value in a file or a failed lookup, and is moved out of the map when found.

**`vireo()` (`src/i18n/vireo.ts`).** Core never imports the catalog (`scienceBoundary.test.ts`), and its literals stay
byte-exact. A screen site wraps the literal; file writers and the F2 mirrors never do. So the same constant can feed a
translated dialog and an English file.
- The dictionary key is the normalised original: single `&` accelerators removed, `&&` kept as `&`, trimmed.
- `vireo(text,'ctx')` separates one English text that needs two translations (key `ctx|text`).
- `scripts/audit-ui-messages.mjs` `auditOriginals` lists every tsx site that renders, outside `vireo()`, a member of:
  - an UPPER_CASE import from `src/core/`;
  - a `*_LITERALS`, `*_CAPTIONS` or `*_NAMES` import from any module (VIREO literals kept beside web text, for example
    `TERMINATE_SLEW_LITERALS`, `RESULTS_EDITORS_LITERALS`, `HOT_LIST_POPUP_LITERALS`, `PRINT_SKY_LITERALS`,
    `HELP_BUTTON_NAMES`);
  - a local alias of either (`const D=SOME_DFM`). (Until ES4 also `const C=m.native`, the Wedge map's VIREO captions; ES4 moved
    them out of the picked map, see its section.)

  It also lists the multi-word literals of the `.ts` presentation modules (`webHelp.ts`, `tour.ts`, `multiSpecText.ts`).
  Each needs a receipt in `src/i18n/vireo-literals.json` (`src/i18n/vireoAudit.test.ts`).
- The baseline receipts every unwrapped site as `pending-translation`. After ES1 (which wraps the Help menu captions and the
  Results Editors names, and moves the tour into a map): 757 sites in 65 files and 112 module literals (webHelp.ts),
  658 receipts.
  Each sub-front wraps its area's sites, or records why one stays English (`native text mirrored in a file`,
  `identifier`).
- After ES2: 418 receipts, 28 of them `identifier` (the observatory's), 390 still `pending-translation` (562 sites in the
  exercise areas of ES3 onwards).

## Numbers

`formatNumber`, `fixed` and `scientific` use the `en-US` number locale in every UI language (`locale`). Spanish and English
outputs are identical; `infrastructure.test.ts` checks a vector of values.

## Dev-only pseudo-locale (qps)

Open `?lang=qps` in the dev server. Every catalog, map and `vireo()` string is wrapped as `⟦…⟧`, its vowels are accented and
it is padded about 35 % longer (the expected Spanish length); `{params}` are kept. Map functions have their result marked
only, since it may carry data.
- Visible text without `⟦` is text that does not go through the catalog, a map or `vireo()` yet.
- A download that contains `⟦` is presentation text that reached a file.
- `src/boot.ts` uses `src/i18n/pseudo.ts` only in an `import.meta.env.DEV` branch, so the production build drops it;
  `scripts/check-i18n-dist.mjs` (part of `npm run build`) searches every text file under `dist/` (the app, `labs/`, the
  sitemap, the original text resources) and fails on `⟦`, a `\u27e6` escape in any case, an HTML character reference or a
  pseudo-locale chunk.

## Tests

- **Release smoke** (`tests/release/pages-smoke.pages.ts`): every route of the production build, and a `?lang=es-419`

- **Vitest.** `locale.test.ts` (the decision), `infrastructure.test.ts` (map ids, lazy maps, bundle map checks, the
  catalog-backed maps, tripwire, fallback catalog, `vireo()`, qps, numbers and export hashes under qps, `settleLanguage`

  exported for `useEnglish.ts` and the tests; app code never calls it.

## F1: screen text that must not become data

The target picker labels (`sky.supportedStarLabel`, `sky.supportedGalaxyLabel`) and the Object X hidden names
(`OBJECT_X_LAB.hiddenName`, `hiddenRowName`) are screen text. ES0 traced them:
- the labels reach the picker, notices, the motion card and the analyser's library notice (`Library.targetLabel`);
- the hidden names reach the picker, notices, the Object ID boxes and the masked radio hot-list rows.

Data uses the source identity (`id`, `sourceLabel`, the student's `ObjX-<ID>` from `objectXDataLabel`). The export-identity
tests guard the result.

## F2: native views that mirror a file

A `<pre>` whose lines are the bytes a Save writes stays English on screen and in print, with a caption in the screen language
and `lang="en"`. Examples are FieldInfoListWindow, NativeTextResults, the PulsarSavedRows raw text and CameraInformationList.
Their column headers are not translated, which would break the fixed-width layout.

## Spanish (ES1 onward)

- `src/i18n/es/es.json`: the catalog, partial until ES-REL (fallback mode), complete since. ES1 covers the shell: `app.*`, `project.*`,
  `session.*`, `error.*`, `instructorMode.*`, `demonstrationMode.banner`, every `*.nav`, the home and first steps (`sky.eyebrow`,
  `sky.title`, `sky.subtitle`, `sky.about`, `sky.local`, `sky.observatory`, `sky.analyzer`, `sky.step1…3Help`),
  `spectrum.tools` and `classLink.cancel` (130 keys).
- `src/i18n/es/maps/`: `appShell`, `helpMenu`, `languageChoice`, `projectLinks`, `tour` (complete) and partial `objectXLab`,
  `polish`, `variableStars` (their header-menu names).
- `src/i18n/es/originals.json`: VIREO's menu captions shown in the shell (Help, Topics..., Websites, 2MASS Catalog, Project
  CLEA, NVO, About This Exercise..., Results Editors, Observational Results, Pulsar Results).
- `src/i18n/es/glossary.json`: every §5.1 row with a fixed Spanish form (an English pattern requires a Spanish stem, plural
  forms allowed), fixed interface names, kept names (Project CLEA, Gettysburg College, VIREO, CLEA, NSF, GitHub, FITS, CSV,
  VizieR, NOMAD, USNO-B1, GSC, 2MASS, SHA-256, JSON) and forbidden forms. The lint applies to the Spanish strings that exist,
  so rows for areas still in English wait for their sub-front. Forbidden words are matched with Unicode word boundaries
  (JavaScript's `\b` is ASCII-only): Spain-only words, usted and its imperatives (haga, elija, pulse, presione, seleccione,
  abra, guarde, escriba, revise, espere, use, cargue; «su trabajo», «su investigación»), voseo (tenés, podés, querés,
  hacé, elegí, apuntá, abrí, guardá, mirá, usá) and the unaccented verb «pulsar» in any form.
- `src/i18n/es/lint-allowed.json` (ES1 review 2): a forbidden word that is correct in one string, with the reason, for that
  string only. Several usted imperatives (use, guarde, cargue, abra, espere, revise, escriba) are also third-person
  subjunctives, and «vale» appears in «vale la pena»; translators record the exception instead of rewording good Spanish.
  Every allowance must still be needed by its string.
- The phone menu button and the header nav's accessible name read «Menú» (both are "Tools" in English; «Herramientas» does
  not fit beside the brand and Help at 320 px). The analyzer's own sidebar nav keeps `spectrum.tools`.
- **VIREO names in the shell's prose** (until ES2 fixes the menu glossary): Spanish first, with VIREO's English name in
  parentheses at its first mention, as in «Modo de demostración (Demonstration Mode)», «Ejecutar ejercicio (Run Exercise)»,
  «Iniciar sesión (Log In)», «Aceptar (OK)». VIREO menu captions shown as captions go through `vireo()` and
  `originals.json`; "Project CLEA" is an official name and stays English.
- `src/i18n/es/identical.json`: the Spanish strings that may equal their English source, each with a reason.
- **Checks** (`src/i18n/es/es.test.ts`, failing on violations): the catalog is a valid partial catalog; every map has the
  English shape (complete for the shell maps); originals keys are normalised literals that exist in the source; the shell is
  100 % Spanish; identical text only with a reason; the glossary; the glyphs `› … ↗ ▸ · — – × ✳`; ¿ ? and ¡ ! paired both
  ways (a closer without an opener and an opener without a closer both fail); every placeholder a map function prints in
  English also printed in Spanish; no HTML; no claim to be CLEA's. Length ratios outside 0.7–1.6 are reported, not failed.
  A small self-test checks that the lint does catch usted, voseo, Spain-only words and unpaired marks.
- **Pipeline** (`scripts/i18n-batch.mjs`): `extract --area <file or prefix>` writes the untranslated keys of an area with their
  English, {params}, usage lines and a length hint; an agent fills `es`; `merge` checks keys and {params} and writes es.json
  in en.json's order; then the Vitest checks run and an independent reviewer agent reads the batch in context (decision 7: no
  human sample).
- **End to end**: `tests/i18n/es-shell.spec.ts` (the chunk, `<html lang>`, the title, an English-versus-Spanish comparison of
  every shell text, the Help menu, the tour, instructor mode, the recovery notice and 320 px) and
  `tests/i18n/language-selector.spec.ts` (the gate, Cancel and Escape, Save, Change and reload in both directions, blocked
  storage, View original). `exports-identity.spec.ts` runs the toolbar's Save investigation in English, qps and Spanish.
- **Dist** (`scripts/check-i18n-dist.mjs`): the Spanish catalog's text, and the Spanish text of the maps and originals,
  appears in exactly one chunk, which `index.html` neither loads nor preloads.
  Since ES2 review 1 it also has a size budget for that chunk: a warning above 150 KB gzip and a failure above 250 KB
  gzip (ES2: about 55 KB gzip; ES5: 118.3 KB). The chunk is not split now; ES5 measured first-render times on throttled
  connections and recommends a per-route-area split before ES-REL (see its section). A minified string may be written as "…", '…' or `…`,
  and the check looks for all three forms.
- **Header layout** (ES1 review 1, C5; a small English CSS change): in the wide-screen sidebar the top row wraps, so Help
  moves under the brand instead of overlapping it when they do not fit (with the CI's DejaVu fonts, in English too), the
  status line wraps instead of being cut off, and the theme options may shrink to stay inside their pill. The pinned row can
  therefore grow (80 px before; 134 px with DejaVu in either language), so the sidebar's `scroll-padding-top` is 11rem: the
  wrapped worst case plus one menu item, so keyboard focus moving up the sidebar is never hidden under it (WCAG 2.4.11;

### The Spanish chunk and the per-area split (ES5 measurement)

The plan left the per-area split of the Spanish chunk to ES5. Measured on the ES5 production build (`npm run build`).

**Method.** `vite preview` serves `dist/` without compression, so the files were served from loopback (127.0.0.1:5175, and
6310 for the projected build) by a small static server that gzips text at level 6, as a CDN would, with `Cache-Control:
no-cache`. Chromium (Playwright's headless shell) loads each page in a fresh context with the cache disabled and CDP
`Network.emulateNetworkConditions`: **Slow 4G** 1.6 Mbps down, 750 kbps up, 150 ms latency; **Fast 3G** 1.44 Mbps down,
675 kbps up, 562.5 ms latency (DevTools' former preset). The tour is marked done. *First render* is `performance.now()` when an
init-script MutationObserver first sees the app's own content: a header menu button for the home page (`/`; the prerendered
`index.html` already has an `<h1>`, so the heading cannot be used) and `.classification-main h1` for the lab route
(`#classification`, a lazy route). The Spanish chunk's time is its Resource Timing `duration`; JS and CSS are the summed
`transferSize` of the `.js`/`.css` resources finished before first render. Five runs each; medians (the five runs were within
about 1 % of each other). Spanish loads are `?lang=es-419`; every Spanish run rendered in Spanish (no fallback to English).

**Sizes.** 118.3 KB is the chunk compressed by `check-i18n-dist.mjs` (Node zlib, gzip level 9); 118.8 KB in the table is the
Resource Timing `transferSize` from the measuring server (gzip level 6, 118,461 B of body, plus the response headers).

**Projection to 100 %.** The chunk is 118.3 KB gzip (409 KB raw) at 61.4 % of the catalog's keys (60.7 % of its English bytes),
half of the VIREO originals and 19 of 31 maps (the two largest English maps, Pulsar and RadioAntenna, about 106 KB of source,
are not started). Scaling each part (catalog 85 KB gzip ÷ 0.607, originals 10 KB ÷ 0.507, maps 27.5 KB plus the unstarted
166 KB of English map source at the same ratio) gives about 240 KB gzip, before the help files (ES-HELP). A throwaway local copy
of `dist/` (not committed) had the Spanish chunk padded with an appended string array of shuffled Spanish catalog words to
244.6 KB gzip (763 KB raw).

## Script groundwork: test fonts (SC1)

- **Why.** Checks for Japanese, Chinese, Hindi and Russian depend on font metrics: Noto Sans CJK's normal line is 1.448 em, and Devanagari ink reaches about 1.9 em. So they run under pinned fonts in their own Playwright config, `playwright.scripts.config.ts` (`npm run test:scripts`; specs `tests/scripts/*.scripts.ts`; loopback port `OPENVIREO_SCRIPTS_PORT`, 6400–6498, default 6420). The main suite keeps its own fonts and metrics.
- **The fonts.** `scripts/test-fonts.mjs` writes `~/.cache/openvireo-test-fonts/scripts/fonts.conf`. Its only folder holds symlinks to DejaVu Sans, Serif and Sans Mono, Noto Sans CJK, and Noto Sans Devanagari, Regular and Bold only (what Ubuntu 24.04 ships).
  - Generic families (including `system-ui` and fontconfig 2.17+'s `sans`/`mono`) resolve to DejaVu.
  - A text's language adds its fallback face: JP for `ja`, SC for `zh-Hans`/`zh-CN`, TC for `zh-Hant`/`zh-TW`/`zh-HK`, Devanagari for `hi`. Russian stays in DejaVu.
  - The script checks the config with `fc-list` and `fc-match -s`. It fails if a profile family is missing, if any other family is listed, or if the folder holds anything but its own symlinks.
  - It prints each file's SHA-256, and keeps fontconfig's cache in a folder named after those hashes, so a font package update cannot leave stale metadata behind.
  - If a font is missing it fails with a coded message and the install command: Ubuntu `fonts-dejavu-core fonts-dejavu-mono fonts-noto-cjk fonts-noto-core`, Arch `ttf-dejavu noto-fonts-cjk noto-fonts`. It never installs anything.
  - `npm run test-fonts -- --profile=dejavu` writes the DejaVu-only fontconfig that the Spanish layout checks above refer to, at `~/.cache/openvireo-test-fonts/dejavu/fonts.conf`; use it with `FONTCONFIG_FILE=…`.
- **Same faces, not the same bytes.** Arch and CI resolve the same faces by name, but only the two Noto Sans CJK collections are byte-identical. On Ubuntu 24.04 the six DejaVu files hash differently, and Noto Sans Devanagari is another version (229,336 and 237,660 bytes there; 243,520 and 250,176 on Arch). SC3 must take the hash list printed by the CI job `scripts` as its reference before setting 1 px tolerances, and re-check any tolerance measured locally against a CI run.
- **What is checked.** `tests/scripts/fonts.scripts.ts` asks Chromium which platform font drew each glyph (DevTools `CSS.getPlatformFontsForNode`), for Japanese, Simplified and Traditional Chinese, Hindi and Russian under the site's sans and mono stacks and the generic families.
  - Latin, Cyrillic, digits and general punctuation must come from DejaVu and everything else from the right regional face: no tofu, and no IPA Gothic, WenQuanYi or Unifont.
  - The zh-Hans “ ” therefore come from DejaVu because the stacks put Latin fonts first; SC3 may choose full-width quotes instead.
  - A named family must reach the Bold files.
  - `npm run test:test-fonts` covers the generator.
- **Chromium behaviour pinned by characterization tests** (Chromium of `@playwright/test` 1.64.1, Linux, test fonts; measured 2026-11-09, stable over repeated runs). These tests pin today's browser so that an update that changes it shows up. Each is a reason SC3's `:lang()` stacks must name the regional family:
  - (a) Under `font-family:sans-serif`, Chromium remembers the fallback face per character and ignores `lang`. A later paragraph of another Han region that shares a character with an earlier one gets the earlier region's face for its whole run:
    - zh-Hans then zh-Hant: both SC.
    - zh-Hant then zh-Hans: both TC.
    - ja then zh-Hant: both JP.
    - Paragraphs that share no character keep their own faces.
    - The memory survives `page.setContent` in the same page; a new page starts fresh.
  - (b) Plain `zh` and `ko` fall back to the JP face.
  - (c) Through generic per-character fallback, weights 550, 600 and 700 all get the Regular CJK and Devanagari files, with `font-synthesis` none or auto, while Latin reaches DejaVuSans-Bold. Only a named family reaches the Bold files: 550 with "Noto Sans CJK SC" named gives NotoSansCJKsc-Bold. The site's buttons are 550.
- **CI.** The job `scripts` in `.github/workflows/ci-cd.yml` runs on `ubuntu-24.04` (pinned, so the font packages do not follow `ubuntu-latest`). It installs the fonts from the Ubuntu archive, the same source Playwright's `--with-deps` uses, so this is no new download source, then runs both checks. `deploy` needs it (plan §5). No pixel screenshots: the checks are geometric or ask the browser which font it used.

## Script groundwork: availability in China (SC6)

**What was measured.** Nothing has been measured from inside mainland China yet. On 2026-11-09 the live page
(https://openvireo.space) was read from outside China. Its script tags, in order, are:
1. an inline script;
2. the ld+json block;
3. the app's `<script type="module" crossorigin src="/assets/index-….js">`;
4. Cloudflare's Web Analytics tag, `<script defer src='https://static.cloudflareinsights.com/beacon.min.js'
   data-cf-beacon='{"token": "REDACTED"}'>`.

So the beacon is deferred and comes after the app's module script [M]. A slow or blocked beacon therefore cannot hold back
the app. While it is pending it does hold DOMContentLoaded and the load event, so the browser's loading indicator may keep
turning after the page is already usable.

**Honest assessment (plan §11).**
- openvireo.space is a custom domain on Cloudflare's global network. It is not blocked by design, but mainland visitors are
  served from edges outside the mainland: slower and less predictable, especially at school hours [I].
- The entry is about 1.0 MB gzip and the GSC sky tiles are 1–2 MB each. On a lossy international link a first load may take
  tens of seconds [I].
- No source confirms or denies blocking of `static.cloudflareinsights.com` or `cloudflareinsights.com` [U]. If they are
  blocked, only the visit counts from China are lost.
- The two live VizieR hosts (`vizier.idia.ac.za`, `vizier.cds.unistra.fr`) are untested from China [U]. The Beijing mirror

## Script groundwork: per-locale lints, plurals and IME (SC4, SC5)

- **Lint framework** (`src/i18n/lint/`). `rules.ts` holds pure rules that take a pair (`catalog:<key>`, `map:<id>.<path>`,
  `original:<key>` with its English) and a `LocaleProfile`, and return typed findings. Errors fail a batch; reports (the
  length ratio) go to the reviewer. Rules use Unicode classes only, never `\b` or `\w`, and a test enforces it.
  - **Rules:**
    - placeholders, as a multiset whose order may change;
    - no HTML;
    - identical-to-English, or no character of the script, only with a reason in `identical.json`;
    - left-over English: three words in a row, each with a lower-case Latin letter, outside brackets and quotes (acronyms and
      format tokens like `YYYY-MM-DDTHH:MM:SS` pass);
    - glossary terms, names and forbidden words;
    - register;
    - claims to be CLEA's or official (denials pass);
    - glyph classes (`...`/`…` and, in ja/zh, `……` are one ellipsis);
    - mark pairs (a VIREO message quoted in English inside “…” keeps its own marks);
    - quote style and typography;
    - Western digits and the decimal point;
    - NFC, invisible and bidi controls;
    - script purity;
    - length band, in grapheme clusters.
  - `lint-allowed.json` entries may name `words`, `placeholders` the translation may add, or whole `rules`, always with a
    reason. Allowances that are no longer needed are flagged.
  - `pairs.ts` collects pairs from a catalog, maps and originals.
  - `pluralForms` requires each key marked plural to have the language's CLDR categories (optional ones may fall back to
    `other`) and none it never selects.
  - Structural checks (`createI18n`, `mapParity`, originals keys) stay as they are.
- **Profiles** (`profiles.ts`) for ja, hi, zh-Hans, zh-Hant and ru. The register is decided (user, 2026-11-09): Japanese
  です/ます, Hindi आप, Russian lower-case «вы», Chinese 你.
  - `REGISTER` holds these values. The alternatives stay expressible, and the fixtures prove each register pattern both ways.
  - Length bands are first proposals that each language's XX0 calibrates: ja/zh 0.3–1.0, hi 0.45–1.2, ru 0.8–1.8.
  - The Simplified/Traditional table in `hanVariants.ts` is a hand-curated seed. Generation from Unihan is not approved as a
    download.
  - `text-autospace` for `:lang(ja)` and `:lang(zh)` belongs to SC3's CSS; the strings carry no manual CJK–Latin spaces
    either way.
- **Mutation fixtures** (`fixtures.ts`): a good and a bad string per rule and language, plus a flipped register per language.
  The good one passes every rule; the bad one trips its rule. They test the rules, not the translations.
- **Plurals** (`src/i18n/plural.ts`): `plural(language, n, forms)` over `Intl.PluralRules`, with the rules cached per language
  and every option. Russian has one/few/many/other, ja and zh only other, and hi puts 0 and 1 in one. The dev pseudo-locales

- **IME** (`src/i18n/imeAudit.test.ts`): every Enter handler with what it is bound to and whether it is guarded.

  `OPENVIREO_REFRESH_PINS=1 npx vitest run src/i18n/plural.test.ts src/i18n/imeAudit.test.ts` and review the diff. The

**Format and storage.** Each translation is authored in VIREO's own file format, so `core/cleaHelp.ts` (and `spectralLines.ts`,

## Spanish: the chunk split by route area (ES-SPLIT)

The plan is `analysis/front-plans/front-i18n-es-split.md` in the research root. Until this front the whole Spanish bundle
(`src/i18n/es/index.ts`) was one chunk that a Spanish load waited for before its first render. It is now split into a **core
module**, which boot waits for, and one **module per route area**, which the area's routes fetch together with their own
JavaScript. English is unchanged and fetches nothing new.

**Sources (unchanged).** `es.json`, `originals.json`, `maps/*.ts` and `es/index.ts` stay the single sources, edited add-only by
the translation fronts; `es/index.ts` is the manifest (map id → file and export) and the whole bundle that Vitest imports. No app
module imports it, the catalog or a map file (`split.test.ts` item 5); no generated file is committed. The split languages are
listed in `src/i18n/languages.json` (`[{"tag":"es-419","dir":"es","catalog":"es.json","budgetFactor":1}]`); a later language adds
one line and its own `src/i18n/<dir>/`.

**Areas come from the code.** A route opts into an area at its own lazy site: `lazyArea('classification',()=>import('./ClassificationLab'))`
(`src/components/lazyArea.ts`). A plain `lazy()` stays in the core, so a missed opt-in costs bytes and never shows English. The
eight areas are declared in `src/i18n/areas.ts` (`AREAS`) and have 16 roots: classification (ClassificationLab); cluster
(ClusterDatabaseLab, NativeClusterAnalysis, ClusterNativeObservationHr, and ClusterDataWindow for File › Cluster Data…);
photometer (Photometer); pulsar (PulsarAnalysis, PulsarSavedRows); radio (RadioTelescopeRoute); lss (LssSurvey, WedgeLab);
exposure (GalaxyExposure, StarExposure, SkyExposure, and FieldSpectrometer in `Spectrometer.tsx`); fits (FitsImageLab). Object X,
the variable stars, the language selector and the observatory windows stay plain `lazy()` (their text is read by the shell too,
or is tiny). There is no help area: ES-HELP's help files are already one chunk each.

**The planner** (`scripts/i18n-split.mjs`, `node scripts/i18n-split.mjs [--json] [--lang es-419]` prints the modules) parses
`src/**/*.ts(x)` with `rolldown/utils` and resolves relative imports as Vite does. Edges are static imports, value re-exports,
dynamic `import()` and plain `lazy()`; type-only imports and type positions are ignored. A file's contexts are `core` when
`src/main.tsx` reaches it without crossing a `lazyArea` boundary, otherwise the areas whose roots reach it. Then:
- **Keys.** The files of a key are those that name it literally (as `scripts/i18n-areas.mjs` finds them) plus those that hold
  any template or `+` head that matches it (`` `pulsar.export.row.${…}` ``, `'fits.error.'+…`), not only the longest (review:
  a shorter head in a core file can build the same key as a longer one in an area file; no key moves today). This is more
  conservative than the plan's "static first, then the longest head" order: a key named in an area file and built from a head
  in a core file goes to the core (5 keys, 0.4 KB). A key with no file, or named or built in the i18n runtime (`src/i18n/*.ts`, for
  example `fieldReasonText`'s head), is core.
- **Maps.** The files that import the picked export (`OBSERVATORY_MESSAGES`…), following re-exports; the defining
  `*Messages.ts` file when the pick is used there too, sits in a translator factory (`createPulsarTranslator`) or is not exported.
- **Originals.** All 748 stay in the core: `vireo()`, `vireoList()`, `vireoMenuItem()` and "View original (English)" are unchanged.
- **Module.** The core if any file is core (or none is reached); otherwise the one area, or a **shared module** named after the
  sorted set of areas (`cluster+photometer`) when files of several areas render it and no core file does. Each area module
  statically imports its shared modules, so Rolldown emits each once and no text is duplicated.

**The plugin** (`openVireoI18nSplit()` in the same file, registered in `vite.config.ts`) serves the plan as virtual modules:
`virtual:openvireo-i18n/loaders` (the only thing in the English entry: `{'es-419':()=>import('virtual:openvireo-i18n/es-419')}`,
used by `src/boot.ts`), `virtual:openvireo-i18n/es-419` (the core: its catalog keys inlined, its map files and `originals.json`
imported, `areas` loaders, `mapModules` and `complete`, and in the dev server and Vitest `keyModules`), `…/es-419/<area>` and
`…/es-419/shared/<a+b>`. Chunks come out as `i18n-es-419-<module>-<hash>.js` (`+` is written `_`). In the dev server a source
change that moves text between modules re-plans (scans are cached per file) and reloads the page. When it builds, the plugin
repeats the visibility check on Rolldown's own module graph (`getModuleInfo(...).importedIds` and `dynamicallyImportedIds`,
crossing only the planner's `lazyArea` boundaries) and fails the build on a mismatch, and checks that the entry's static graph
reaches no language module. `src/i18n/virtual.d.ts` types the virtual modules.

**Runtime.**
- `activateLocale` builds a split bundle always with the English fallback, since its catalog is never complete in one module.
  **ES-REL must keep `!!bundle.areas` there when it flips `SPANISH_RELEASED`** (it did).
- `loadArea(name)` (`src/i18n/areas.ts`) resolves at once without `areas` (English, the pseudo-locales, a failed boot), so English
  imports nothing. Otherwise it fetches the area once per activation, races `LANGUAGE_TIMEOUT_MS` (10 s) from its own start, adds
  the part with `extendLocale` (the holder is replaced: catalog rebuilt, maps merged, `areas` records `loaded`), or marks the area
  `failed`. It never rejects, and a part that arrives after the timeout is ignored. `lazyArea` runs it with the route's import in
  `Promise.all`, so both start together and a route JS failure still reaches `LazyBoundary`'s "site updated" notice.
- **Reads before an area arrives.** `t` (one null test in English) and `resolveMessages` call `notePendingText` when the active
  split language lacks a key or a map: text of a loaded or failed area is English without an error; text of an area still
  loading **throws in the dev server and Vitest** (`OpenVireo: text "<key>" was read before its area <m> loaded`, the tripwire,
  from `keyModules` and `mapModules`); in production it is answered in English, counted (`pendingTextRequests`) and logged once
  per area (keys: once per load, and only when `complete`, which ES-REL sets, since before it production cannot tell a pending key
  from an untranslated one).
- `lazyMessages` and `lazyTranslator` keep a built map or translator only when no read during the build was pending, so text read
  too early becomes Spanish once its area arrives. A read of `$$typeof` on a lazy map answers `undefined` without building it
  (review): React Refresh probes it on every capitalised module-level value as the module evaluates in the dev server
  (`RADIO_SAVE_TEXTS` in `RadioReceiverWindows.tsx`), which read the radio text before its area and was hidden by Refresh's own
  `try`. The dev tripwire logs an `Error` (with its stack) before it throws, so such a caught read is no longer silent.
- **An area that fails** (an error, a wrong part, or 10 s) leaves its route in English with one bilingual `role="status"` notice in
  the shell next to the boot notice (`AREA_FAILURE_NOTICE`, `data-testid="area-failure"`): «No se pudo cargar parte del texto en
  español; esa parte se muestra en inglés. Recarga para intentarlo de nuevo.» The rest of the site stays Spanish.
- After a deploy, `/assets/*` stays immutable; a tab opened earlier fails a lab it had not visited like any route chunk (the
  route error if its JavaScript is gone, English and the notice if only its area is). The core chunk names the area chunks, so
  any area's text change also changes the core's hash.

## Script groundwork: the language registry, detection and selector (SC8)

The plan is §7 and §9 of `analysis/front-plans/front-i18n-scripts.md`, with the five additions of
`analysis/front-plans/front-i18n-pt-br.md` §1.3 that a second, partial language needs (research root). Until this front the
release gate was one flag, `SPANISH_RELEASED`, and about twenty places named es-419. Now every translated language is one line of
a registry, and Spanish behaves exactly as ES-REL released it.

**The registry.** `src/i18n/languages.json` stays the single list, one line per language, because the Node build scripts read it
without compiling TypeScript (`scripts/i18n-split.mjs` plans each language's chunks, `scripts/check-i18n-dist.mjs` checks them,
`i18n-batch.mjs` and `i18n-coverage.mjs` take `--lang <tag>`). `src/i18n/languages.ts` types it and holds the pure rules the app
needs. English is the source language and is not in the list. The fields:

| Field | Meaning |
|---|---|
| `tag` | the `?lang=` value, the stored value and the bundle's `language`; exact and case-sensitive (`es-419`, `pt-BR`) |
| `dir`, `catalog` | `src/i18n/<dir>/` with `<catalog>`, `originals.json`, `maps/`, `index.ts` (the manifest) and, with `help`, `help/` |
| `budgetFactor` | multiplies the chunk budgets of `check-i18n-dist.mjs` (1 for Latin and Cyrillic; 1.4–1.6 planned for CJK and Devanagari) |
| `htmlLang` | `<html lang>`, and the `lang` of the language's option and failure notice |
| `pagePath` | the site path of the language's own static pages, `dist/<pagePath>/…` (`es`; pt-BR will use `pt-br`), which may carry its text |
| `autonym`, `englishName` | the selector's option (the autonym, plus the English name when it has no Latin letter: `日本語 (Japanese)`) and the English half of the failure notices |
| `match`, `except` | browser language ranges (below) |
| `released` | the release gate of decision 5 |
| `help` | `{"related":"…"}` when the language translates all 38 help files: its "RELATED TOPICS" marker |
| `notices` | the language's own sentences for "could not be loaded" and "part of the text could not be loaded" |
| `path` | tests only: a root-relative directory instead of `src/i18n/<dir>` (the fixture below) |

Spanish's line: `es-419`, dir `es`, page path `es`, «Español», match `es`, released, help «TEMAS RELACIONADOS», and the two notices that were
`LANGUAGE_FAILURE_NOTICE` and `AREA_FAILURE_NOTICE` (their English halves are built from `englishName` and read exactly as before).

**Detection** (`decideLocale`, `src/i18n/locale.ts`; `matchLanguage`, `src/i18n/languages.ts`). One load decides once:
1. `?lang=<tag>`: English or **any** registered language, released or not (the preview); that load only, never stored;
2. the stored choice: English or a **released** language;
3. the first browser language: the registered language whose `match` range covers it most specifically (RFC 4647 basic
   filtering, any case: a range covers a tag equal to it or starting with range + `-`), unless its `except` covers it at least as
   specifically; English when that language is not released, or when none matches. Only the first preference decides, and an
   unreleased first preference gives English, never the second preference.

So `es`, `es-MX`, `ES-ar` give Spanish exactly as before; `?lang=ES-419` and `?lang=es` are no tag (English); the dev-only
pseudo-locales are link values only. For the languages to come the ranges are those of the plans: `pt` (pt-PT and pt-AO get pt-BR,
`gl` does not), `fr`, `id`, `hi`, `ja`, `ru` (never `uk`, `be`, `kk`), `zh-Hans` with `zh-Hans`, `zh-CN`, `zh-SG`, `zh-MY` and bare `zh`
and `except` `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`, and later `zh-Hant` with those four. The script subtag beats the region
(`zh-Hant-CN` is Traditional, `zh-Hans-TW` Simplified), and while zh-Hant does not exist a Traditional-Chinese browser opens
English, with Simplified offered in the selector once it is released (decision of 2026-11-09). `tests/fixtures/i18n/registry.ts`
holds those entries for the tests only; each language adds its own line in its first front. The plan's case-insensitive `?lang=`
and its `zh-CN`/`zh-TW` link aliases were not adopted: ES-REL's tests pin exact tags, and detection covers browsers anyway.

**The gate, per language.** `released` replaces `SPANISH_RELEASED` everywhere it acted:
- `activateLocale` (`src/i18n/active.ts`) builds with the English fallback a split bundle (as since ES-SPLIT) or a language before
  its release; only a whole released bundle (Vitest's `src/i18n/es/index.ts`) builds strictly;
- `resolveMessages` (`src/i18n/registry.ts`) completes a partial map with English for a language before its release (a map of the
  wrong shape still throws in the dev server and tests); a released language's maps must be complete;
- the planner reports a released language whose catalog does not cover en.json as a problem, which fails the build;
- `check-i18n-dist.mjs` requires marker text for every module of a released language.

**The selector** (`src/components/LanguageChoice.tsx`). A native `<select>` replaces the two-option pill, in the same place at the
foot of the header menu, drawn like the theme switch: one row for any number of languages, with keyboard, touch and screen-reader
behaviour from the platform. Its accessible name is the map's `legend` («Idioma / Language», visually hidden as before). It lists
English, every released language and, on a preview load, the previewed language, in registry order; each option is its autonym in
its own `lang`. It is shown when it offers a choice (`selectorShown`): on every load since ES-REL, never under the pseudo-locales,
and, if no language were released, only on a preview load. The confirmation, Save investigation, Cancel and Escape, the storage
rules and View original are unchanged; the dialog names the language by its option text. On a preview load nothing is stored (ES1
review 1, C2, now for every language before its release): the choice travels as `?lang=` and the dialog shows the preview note,
so a tester's choice cannot start applying once that language is released. The map `languageChoice` lost `english` and `spanish`
(the options come from the registry; `src/i18n/es/identical.json` lost their two entries). Test ids: `language-select`, and
`language-<tag>` on each option.

**Failure notices.** `failureNotice(kind, tag)` builds both from the registry; the shell renders the language's half with its
`htmlLang` (`lang="es-419"`, before `lang="es"`).

**Help files.** Each help module now names its `language` (the 38 Spanish ones gained `export const language='es-419'`). The loader
(`src/help/helpTranslation.ts`) looks in `src/i18n/<dir>/help/` of this load's language, offers the translation when the
language's entry has `help`, refuses a module of another language, and `relatedMarker(view)` gives the language's marker
(`RELATED_MARKER` is the original's). `check-i18n-dist.mjs` assigns each help chunk to the one registered language whose quoted tag
it holds and requires 38 chunks, one per help file, for each language with `help` and none for the others. Two languages' help
modules for an empty original (MLTSPHLP.LST, SPLSTHLP.LST) therefore stay distinct chunks.

**A partial language before its release.**
- *Planner* (`scripts/i18n-split.mjs`): `languageDir(language)` is `src/i18n/<dir>` (or a fixture's `path`). For a language before its
  release, an area with no keys, maps or shared modules is not a problem but `empty`: the core's `areas` entry resolves at once to
  an empty part (`Promise.resolve(...)`, no `import()`), so it has no chunk and `loadArea` marks it loaded. The gate is `released`,
  not a complete catalog (SC8 review): the `pulsar` area holds only maps, so a language whose catalog is complete before its maps
  has it empty. For a released language an empty area is a problem, as before.
- *Runtime*: a key the partial catalog lacks is English without the tripwire (its bundle is not `complete`, and `keyModules` lists
  only keys it has); a map it lacks is English; a partial map is completed with English.
- *Dist check*: a text that another registered language's sources also hold (catalog values, map literals, originals) is no
  marker, so a Portuguese word equal to a Spanish one is not reported as misplaced; an empty area must have no chunk; a module of
  an unreleased language with no marker yet (short or English-equal texts) is found by its chunk name, with a warning. A
  language's own static pages, an `.html` file under `dist/<pagePath>/` (ES-SEO's `dist/es/index.html`, `dist/es/labs/…`), may carry
  that language's text (its lab names, say), never another language's; an `.html` file elsewhere (`dist/labs/…`) and every `.js`
  file outside the language's chunks, also under its path, keep the rule (coordinator's addition for ES-SEO). The script
  is now a function, `checkI18nDist(dist, {root, languages, graph})`, with the same command line.
- *Tests*: `src/i18n/split.test.ts` loops over every registered language (its whole bundle from `src/i18n/<dir>/index.ts`, its core
  from the loaders) and plans the fixture.

**Adding a language** (what PT0 does for pt-BR):
1. Add its line to `src/i18n/languages.json` with `"released":false`, no `help`, its `notices`, `match` (pt-BR: `["pt"]`) and
   `budgetFactor`; dir in lower case (`pt-br`).
2. Create `src/i18n/<dir>/` like `src/i18n/es/`: `<catalog>.json` (any subset of en.json), `originals.json` (may be `{}`), `maps/`,
   and `index.ts` exporting the whole `LocaleBundle` with `language:'<tag>'` and `maps:Object.freeze({...})` (the manifest the planner
   parses); its lints, glossary and test as SC9's framework and the language's profile require.
3. `npm run build`: the planner gives it a core, its non-empty areas, and empty areas without chunks; `check-i18n-dist.mjs` lists
   them. `?lang=<tag>` previews it; nothing detects, stores or offers it otherwise. Vitest keeps a module cache
   (`node_modules/.vitest-cache`) in which an `import.meta.glob` keeps the directories it saw: after adding `src/i18n/<dir>/`, delete
   that cache once, or `split.test.ts` and `languages.test.ts` miss the new directory locally (CI starts without it).
4. Its help front adds `src/i18n/<dir>/help/<NAME>.ts` for all 38 files (each with `language`) and `help` in the registry line.
5. Its release front sets `"released":true` once the catalog and maps are complete (the planner, `split.test.ts` item 7 and
   `check-i18n-dist.mjs` enforce it), which turns on detection, storage and the option for everyone.
