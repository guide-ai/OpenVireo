# Languages (I18N)

OpenVireo is English today. Spanish (es-419) is being added (user decisions of 2026-11-09, AGENTS.md, last paragraph; plan
`analysis/front-plans/front-i18n-es.md` in the research root). This file describes the infrastructure that Front ES0 added.
Nothing visible changed with ES0: no selector, no auto-detection, no Spanish text.

## What a translation is

- Translations are **web adaptations by OpenVireo**. They never claim to be CLEA's.
- CLEA's original bytes, hashes, manifests and provenance do not change.
- **Files the site writes stay English** and byte-identical in every language (decision 3). This covers TXT, FITS, CSV,
  HTL, PLR, saved investigations, sessions, options files and every other export.
- **Text on screen that mirrors a written file** (a native list window, a results preview) stays English, with a caption in
  the screen language (decision 9, F2 below).
- **Numbers keep the decimal point** on screen in every language, as typed inputs and files do (decision 4).
- The Spanish addresses the student as **tú** (decision 6).

## The language of one load

The language is settled once per page load, in `src/boot.ts`. `src/main.tsx` imports it first; its body runs synchronously
before any later import of `main.tsx` evaluates. `index.html` and the entry are unchanged.

1. **Decide** (`src/i18n/locale.ts`, `decideLocale`, a pure function):
   1. a `?lang=` link parameter: `en` or `es-419` (`qps` only in the dev server). It applies to that load and is not stored;
   2. the stored choice: localStorage `openvireo-language`, read in a try/catch;
   3. the browser language: the first entry of `navigator.languages` decides; `es`, `es-MX`, `es-ES`… give es-419, and
      everything else gives English.
2. **Release gate (decision 5).** Until ES-REL, `SPANISH_RELEASED` is `false`: steps 2 and 3 are skipped, so only an explicit
   `?lang=es-419` preview link asks for Spanish.
3. **Bundle.** English needs none. Spanish has none until ES1 adds `src/i18n/es/`, so in ES0 a `?lang=es-419` load is
   entirely English, with `<html lang="en">`. The dev-only pseudo-locale is built synchronously from the English sources.
4. **Activate** it (`activateLocale`), set `<html lang>`, and, for a non-English load, `document.title`.

Every module that builds text at import time (module-level `t()` calls, the `pickMessages` maps) evaluates after boot, so it
sees the chosen language. That is why the ~62 static importers of `t` need no change.

`src/boot.ts` statically imports only the catalog machinery: `src/i18n/catalog.ts` (`createI18n`, the types, the English
instance), `active.ts` (the active language) and `locale.ts`, plus `pseudo.ts`, which the production build drops with its
`import.meta.env.DEV` branch. `src/i18n/index.ts` re-exports them with `t`.

**Tripwire.** In the dev server and in Vitest, asking for text before the language is settled throws. It catches a module that
would build text before boot ran. In production the same case falls back to English. The active language is kept on
`globalThis` (`Symbol.for('openvireo.i18n.active')`), so a re-evaluated copy of the module (a hot update, `vi.resetModules`)
keeps it.

Entries that do not go through `main.tsx` import `src/i18n/useEnglish.ts` first: the Vitest setup (`vite.config.ts`) and the
standalone test harnesses under `tests/harness/`.

### Why boot is synchronous in ES0 (a deviation from the plan)

The plan made `src/boot.ts` the page entry, loaded the Spanish bundle lazily and then ran `await import('./main')`, with a
Vite plugin that preloads the app chunk in `index.html`. That was built and measured, and it changed three things:
- **The window load event** no longer waited for the app: a dynamic import does not delay it. Tests that act right after
  `page.goto()` (for example `focus-after-layout.spec.ts` and `cluster-native-observation-hr.spec.ts`) failed, because
  `goto()` returned before the app had evaluated. A top-level await in the entry does not delay the load event either.
- **Rolldown's chunks** changed: with the app as a dynamic entry, six small shared chunks appeared and five disappeared,
  and the app's CSS came out in another module order (`help.css` became its own file; `hubble-lab.css`,
  `spectrum-engine.css` and `help.css` moved before the base styles). The computed styles of every element were compared on
  twelve routes and six menu and phone states, with no difference, but the order was no longer Vite's own.
- **Size:** +3.2 KB gzip on the files `index.html` loads (+2.2 KB raw), mostly chunk overhead.

A top-level await in the catalog module, to keep `main.tsx` as the entry, split the entry far more (+13.6 KB gzip).

ES0 has nothing to load asynchronously (no Spanish yet, and qps is built in place), so boot is synchronous: the entry, the
chunks, the CSS (byte-identical), the preloads and the load event are those of before. **ES1 must choose how the Spanish
bundle arrives before the app evaluates.** A single entry cannot import the app statically for English and dynamically for
Spanish. The options found are: (a) the plan's dynamic app import for every load, accepting the load-event, chunk and size
effects above (the English suite would then need to wait for the app after `goto()`); or (b) a second entry page for Spanish
whose entry statically imports the Spanish bundle before `main.tsx` (it fits ES-SEO's `/es/`), with Spanish loads of `/`
sent there.

**Loading cost.** Measured with `npm run build` on the files `index.html` loads (gzip and brotli per file):

| | raw | gzip | brotli |
|---|---|---|---|
| main 033f693 | 4,005,050 | 1,011,899 | 740,546 |
| ES0 | 4,006,950 (+1,900) | 1,012,782 (+883) | 741,419 (+873) |

The i18n chunk merges into a shared chunk, so the page loads one file fewer. Every CSS file is byte-identical.

## Three kinds of text

| Source | How it is translated | Where the translation lives (from ES1) |
|---|---|---|
| `src/i18n/en.json` (`t`) | `t` delegates to the active catalog; missing keys fall back to English until ES-REL | `src/i18n/es/es.json` |
| The 25 `*Messages.ts` files (30 maps) | `export const X=pickMessages('id',X_EN)`; the 7 flat translators default to `pickMessages('id',X_EN)` | `src/i18n/es/maps/<id>.ts`, typed `Translation<typeof X_EN>` |
| VIREO's own literals in `src/core/` | opt-in at each render site: `vireo(LITERAL)` | `src/i18n/es/originals.json`, keyed by the normalised original |

**`*Messages.ts` maps.** Consumers read the picked name (`CAMERA_MESSAGES`, `CLUSTER_HR`, `OBJECT_X_LAB`, …). The `_EN` name
is the typed English source; tests and the Spanish maps use it. In English, every picked map is the English map itself.
`src/i18n/parity.ts` (`mapParity`) checks a translated map against its English map: the same keys at every depth, the same
kind, the same `{param}` set and the same function arity.

**`vireo()` (`src/i18n/vireo.ts`).** Core never imports the catalog (`scienceBoundary.test.ts`), and its literals stay
byte-exact. A screen site wraps the literal; file writers and the F2 mirrors never do. So the same constant can feed a
translated dialog and an English file.
- The dictionary key is the normalised original: single `&` accelerators removed, `&&` kept as `&`, trimmed.
- `vireo(text,'ctx')` separates one English text that needs two translations (key `ctx|text`).
- `scripts/audit-ui-messages.mjs` `auditOriginals` lists every tsx site that renders a member of an UPPER_CASE import from
  `src/core/` outside `vireo()`, plus the multi-word literals of the `.ts` presentation modules (`webHelp.ts`, `tour.ts`,
  `multiSpecText.ts`). Each needs a receipt in `src/i18n/vireo-literals.json` (`src/i18n/vireoAudit.test.ts`).
- The ES0 baseline receipts every site as `pending-translation` (484 sites in 57 files, and 128 module literals). Each
  sub-front wraps its area's sites, or records why one stays English (`native text mirrored in a file`, `identifier`).

## Numbers

`formatNumber`, `fixed` and `scientific` use the `en-US` number locale in every UI language (`locale`). Spanish and English
outputs are identical; `infrastructure.test.ts` checks a vector of values.

## Dev-only pseudo-locale (qps)

Open `?lang=qps` in the dev server. Every catalog, map and `vireo()` string is wrapped as `⟦…⟧`, its vowels are accented and
it is padded about 35 % longer (the expected Spanish length); `{params}` are kept. Map functions have their result marked
only, since it may carry data.
- Visible text without `⟦` is text that does not go through the catalog, a map or `vireo()` yet.
- A download that contains `⟦` is presentation text that reached a file.
- `src/boot.ts` uses `src/i18n/pseudo.ts` only in an `import.meta.env.DEV` branch, so the production build drops it;
  `scripts/check-i18n-dist.mjs` (part of `npm run build`) fails if `dist/` contains `⟦` or a pseudo-locale chunk.

## Tests

- **English suite.** Playwright pins `locale:'en-US'` in all three configs; Vitest activates English in its setup file.
- **Exports identity** (`tests/i18n/exports-identity.spec.ts`). Each family is downloaded in English and in qps from the
  same deterministic path; the file names and SHA-256 must be equal and the qps bytes must not contain `⟦`. Covered in ES0:
  - measurement CSV, velocities CSV, analysis session JSON;
  - Hubble CSV and Hubble session JSON;
  - complete investigation JSON, classification CSV, observation notebook, native TXT (unchanged bytes) and the generated
    native CSV;
  - HTL save;
  - the options file (`VEO_OPTS.json`);
  - variable-star Save Text (As Displayed);
  - the pulsar results CSV;
  - the star spectrum `.SSP` save;
  - the CCD camera FITS and VIREO-header FITS. Their header is compared with the wall-clock and random-stream cards
    (`DATE-OBS`, `MJD-OBS`, `RA`, `DEC`, `CRVAL1`, `CRVAL2`, `CAMSEED`) masked, because every pixel depends on `CAMSEED`.

  Not yet covered: Object X FITS, LSS TXT, PLR and the native pulsar save, native `.DAT` observations, photometer JSON, the
  cluster TXT and the radio raw export. Each exercise sub-front adds its own families, and Spanish joins every family from
  ES1.
- **Vitest.** `locale.test.ts` (the decision), `infrastructure.test.ts` (maps, tripwire, fallback catalog, `vireo()`, qps,
  numbers and export hashes under qps), `vireoAudit.test.ts` (receipts).

## F1: screen text that must not become data

The target picker labels (`sky.supportedStarLabel`, `sky.supportedGalaxyLabel`) and the Object X hidden names
(`OBJECT_X_LAB.hiddenName`, `hiddenRowName`) are screen text. ES0 traced them:
- the labels reach the picker, notices, the motion card and the analyser's library notice (`Library.targetLabel`);
- the hidden names reach the picker, notices, the Object ID boxes and the masked radio hot-list rows.

Data uses the source identity (`id`, `sourceLabel`, the student's `ObjX-<ID>` from `objectXDataLabel`). The export-identity
tests guard the result.

## F2: native views that mirror a file

A `<pre>` whose lines are the bytes a Save writes stays English on screen and in print, with a caption in the screen language
and `lang="en"`. Examples are FieldInfoListWindow, NativeTextResults, the PulsarSavedRows raw text and CameraInformationList.
Their column headers are not translated, which would break the fixed-width layout.

## Tools

- `node scripts/i18n-areas.mjs`: which files render each en.json key (static `t('key')`, then prefix rules for keys built at
  run time).
- `node scripts/i18n-coverage.mjs`: per key prefix, how much of en.json, the maps and the originals has Spanish (0 % in ES0).
