# I06 subflow: radio telescope control panel — Tracking, Slew Rate, Set Coordinates and programmed slew

This slice recovers one supported user flow inside the original radio control panel (`TRadioLab`, VMT `0x563a08`):

**Tracking → Slew ▸ Set Coordinates… → coordinate entry and validation → confirmation → programmed slew → arrival, or stop/resume/cancel → reopen.**

It sits on top of the main-window switch/access slice ([RADIO-CONTROL.md](RADIO-CONTROL.md)). Contracts RA-01…RA-19 are listed in [RADIO-ANTENNA-PROVENANCE.json](RADIO-ANTENNA-PROVENANCE.json), with address ranges, decoding routes, inferences and gates. Artifact: VIREO 1.504 `CLEA_VEO.exe`, SHA-256 `781bc970…c54c`. No original code was executed or emulated.

I06 is **not** complete. This slice itself implements no receiver or signal. Later bounded increments, each with its own gaps, now provide:
- model-generated receivers and pulsar signals ([RADIO-RECEIVER-SIGNAL.md](RADIO-RECEIVER-SIGNAL.md), [RADIO-RECEIVER-MONITOR.md](RADIO-RECEIVER-MONITOR.md));
- the date dialog before activation (RC-12…RC-17 in [RADIO-CONTROL.md](RADIO-CONTROL.md));
- the full nine-field numeric options dialog (R-RX9), only under an explicit in-memory numeric authority ([RADIO-SIMULATION-OPTIONS.md](RADIO-SIMULATION-OPTIONS.md)).

Still not implemented: the beam object, the hot list's Add Current Item and Save Updated List, the date dialog's post-activation hook and local-date labels, the options file (INI loading and writing) and the classroom, Files... and Site... owners of the options. Native equivalence is not established. Set Coordinates accepts J2000.0 or B1950.0 entry with the recovered fixed-epoch conversion and its original flag lifecycle (RA-EP-01…RA-EP-04); see "Epoch of Input Coordinates" below. The panel clock's hour-angle/RA bookkeeping (RA-13) runs only from an explicitly supplied web UT scenario. Manual N/S/E/W press-and-hold (RA-16…RA-18) moves the pointing; see "Manual N/S/E/W hold" below. The native keyboard table (RA-19) is mapped only in part (letters and NumLock-on keypad keys inside an explicit key scope; F4/F8 decoded but not used); see "RA-19 keyboard table" below. The altitude (horizon) limit (RA-12) runs at its three callers when the recovered Limit Slewing option is on, under a conditional browser admission policy; see "Altitude limit (RA-12)" below. Slew ▸ Hot List ▸ View/Select and Load (RA-HL-01…RA-HL-07) work on the HTL list shared with the observatory editor; see "Hot list" below. Nothing here acquires or simulates a signal.

## Recovered behavior (implemented in `src/core/radioAntenna.ts`)

| Dialog prefill | `FormActivate` splits the values into d/m/s with second→minute carry. RA seconds use ffFixed 2 and Dec seconds ffFixed 1. Dec degrees are shown as `IntToStr(sign×deg)`, so a Dec in (−1°, 0°) shows `0` without its minus. | `skyCoordsFieldsFor` |

This also happens with the instant option; the telescope then jumps straight to the target without using the rate. Otherwise N/S/E/W and Rate are disabled and SlewTimer2 starts. | `answerNotice` |
| SlewTimer2 | The slew runs Dec first, then RA. RA takes the short way (Δ negated when \|Δ\| > 12 h). The RA step is rate×≈1/3600/15, computed once at the Dec→RA switch. Arrival uses the inclusive comparisons and the [0, 12) h crossing window. An initial \|ΔRA\| ≤ ≈1e−5 h finishes in that same switch callback without snapping: the RA step is stored but never added. Completion re-enables N/S/E/W and Rate and shows an information box. | `slewTimerTick` (100 ms nominal) |
| Stop | Yes in the stop question: slewing off, the position stays where it is, controls are re-enabled. No: SlewTimer2 resumes. | `answerNotice('stop-slew')` |

Otherwise RA := normalize(LST − HA). Dec is never written. | `radioClockTick` with an explicit reading from `src/core/radioClock.ts` (WEB-CLOCK-01); nominal 1000 ms browser interval or manual tick (WEB-TIMER-02) |
| HA bookkeeping | The slew request keeps a local HA = LST − target RA (LST only on the transit path). The instant branch stores it. SlewTimer2 RA phases subtract each RA change from HA before normalizing RA. | `confirm-slew` notice `hourAngle` (captured at OK, never replaced at Yes), `startSlew`, `slewTimerTick` (WEB-HA-01 for an unknown HA) |
| Manual press (RA-16) | N/S/E/W `MouseDown` (left button, latch clear) writes the direction to `+0x53d` and the step to `+0x525`: N rate×K, S (−rate)×K, E rate×K/15, W (−rate)×K/15 (K ≈ 1/3600). | Manual tick (RA-18) | `SlewTimerTimer` (100 ms): N/S add (pole flag clear) or subtract (flag set) the step to Dec; past \|Dec\| > 90 the flag toggles, Dec := ±180 − Dec, RA and HA gain 12 h and the N/S captions swap. | Keyboard table (RA-19) | `FormKeyDown`/`FormKeyUp`: 0x65 guard, latch, table 69…119; KeyDown calls `+0xd4` then the MouseDown, KeyUp the MouseUp of the key's own button (no held-direction check). | `radioKeyboard.ts` (`ra19Dispatch`, `browserTableKey`), `releaseManualSlewThrough`, `manualButtonLeftDisabled` |

Original quirks are kept on purpose:

- **Lost Dec minus:** the Dec minus is lost for −1° < Dec < 0° when the dialog is re-opened.
- **Tracking off mid-slew:** turning Tracking off during a slew hides Set Coordinates, so that slew cannot be stopped. On arrival the slew still re-enables N/S/E/W while Tracking stays off.
- **Rate stays raised:** a programmed slew leaves the rate index at the options maximum, or at a higher index kept from earlier options (the start loop only raises it). The panel's start message therefore names "the rate shown under Slew Rate", not "the maximum rate".
- **No 24 h wrap in the display:** the dialog's RA display shows 23:59:59.996 h as `24 0 0.00`.

## Explicit gates (nothing invented)

- **Radio clock time (RA-13, WEB-CLOCK-01):** the original reads host local time plus an offset set in its date dialog, and its JD includes the optical time zone. None of these is represented. The learner applies a UT (1900–2099, whole seconds; running time up to `2099-12-31T23:59:59.999Z`) and, separately, the compiled radio longitude (−1.393499963671317 rad, record+0x8f4; no site name implied). There is no default, and nothing is imported from the host or the observatory clock, although natively both panels share one date. Without a supplied UT no tick runs and RA stays fixed. Past the range end the scenario stops; nothing is clamped and the antenna keeps its last accepted tick. JD/LST are binary64, with no certified error bound against x87.
- **Not shown or simulated in the tick:** the date, local time and UT LED labels (JD and LST are shown as browser diagnostics, and HA, which the original panel does not display, is labelled as such), the beam `0x561e88` (called on every native tick) and the receiver tail (`[0x5b5b44]` is nil until Receiver is pressed). The date dialog `0x58b2ec` is ported only before activation (RC-12…RC-17 in [RADIO-CONTROL.md](RADIO-CONTROL.md)): its OK sets the scenario UT through `applyRadioClockDialogUT` (WEB-DATE-03), keeping the running or paused state and the longitude, and changes nothing on the antenna; its post-activation hook `0x565ab0` is not ported.
- **Altitude limits (RA-12):** see "Altitude limit (RA-12)" below. With Limit Slewing on and no supplied UT, a slew request stores the coordinates and stops at `limits-require-clock`, and manual slewing waits for an accepted clock tick (`manual-limits-clock`).
- **B1950.0:** no longer gated. The conversion and its lifecycle are recovered (RA-EP-01…04, "Epoch of Input Coordinates" below); its confirmation literal `0x5672f8` is still not decoded.
- **Options owners:** the INI loader `0x5a829c`, `TRadiOptsDlg` (VMT `0x5a7c84`) and classroom files can change every option. Only the compiled defaults are recovered, and the supplied distribution has no `VEO_OPTS.INI`. At startup the App offers only the Limit Slewing flag through an explicit web scenario (WEB-ALT-03). Since R-RX9 the full numeric `TRadiOptsDlg` form exists only under an explicit in-memory numeric authority, and its record is projected onto the antenna options ([RADIO-SIMULATION-OPTIONS.md](RADIO-SIMULATION-OPTIONS.md)). The INI loader, classroom files, Files... and Site... are still not ported.
- **Literals:** message-box texts, status texts, the ClockLbl captions and the RateLbl table are shown in OpenVireo wording, and the UI says so. The RA-12 limit-path literals are now typed-decoded, but they are still not shown.
- **Not modelled:** the browser use of the RA-19 F4/F8 table entries and the native `+0xd4` result on a disabled or hidden button, the pole call `0x408c44` (probably a sound), the Receiver window inside this slice (the receivers are separate increments, [RADIO-RECEIVER-MONITOR.md](RADIO-RECEIVER-MONITOR.md)), the hot list's Add Current Item (`PListAddClick`) and Save Updated List (`PListSaveClick`), beam/sky object `0x561e88`, LED digit rendering, the non-first `FormActivate` path, and Windows timer/message-loop timing.
- **Numerics:** binary64 only. Extended constants are rounded once. `StrToFloat` is a strict web grammar with `.` as the decimal separator and an exponent of at most two digits. Coordinate entry follows the web numeric domain below. Arrival can differ from x87 by one callback at exact boundaries; no tolerance is added.

## Epoch of Input Coordinates (RA-EP-01…RA-EP-04)

Evidence: the 18 canonical listings and 38 typed cells of `/tmp/clea-static-research/radio-epoch-preparation/CANONICAL-EPOCH-EVIDENCE.json` (SHA-256 `d3c1d043…66ec`), plus the supplemental `radio-request-slew.asm` `0x566bc4..0x5671b6` (SHA-256 `3983f6d1…0885`, `REQUEST-SLEW-SUPPLEMENT.json`). Disassembly: GNU objdump `-d -M intel --no-show-raw-insn` (coordinator). REA section-header record `ev_e38712cf…` places the globals `0x5bc1c0`/`0x5bc1cc` in `.bss`. The `*-initial-unverified.asm` sweeps were not used. Listing hashes, typed cells (address, kind, exact ratio, Number, cell SHA-256) and contracts are in the provenance file, section `epoch`.

**Calculation (RA-EP-01, `src/core/radioEpoch.ts`).** `Precess 0x4b9f64` rotates a record (+3 epoch JD, +0xd RA rad, +0x17 Dec rad) with the ζ/z/θ polynomials in T = (E0 − 2451545)/36525 and t = (E1 − E0)/36525, in arcseconds, each converted by (x/3600)·π/180. Then α = ArcTan2(a, b) + z, wrapped by `Frac(α/2π)·2π` and +2π when not ≥ 0. The Dec branch tests the **source** Dec: if 0.01 ≥ π/2 − |δ0| (inclusive) it takes `ClampAcos(√(b² + a²))`, which is never negative, otherwise `ClampAsin(c)`. Clamps set |x| > 1 to exactly ±1 and let NaN through; ArcSin/ArcCos are the native `fpatan` forms. Equal (or unordered) epoch JDs return without writing. Fixed epochs: J2000 = JD 2451545 exactly; B1950 = the Extended immediate 2433282.423500000000103682…, which rounds once to 2433282.4235. The operand direction of `fsubp`/`fsubrp`/`fdivp` is an inference anchored by ArcSin `0x427000` (it must give 1 − x²) and confirmed at `0x4ba2c4` and `0x4ba307`.

**Callers and flag (RA-EP-02…04, `src/core/radioAntenna.ts`).**
- `FormCreate` zeroes the globals and `+0x3c5` (`0x4f312a`).
- `FormActivate` (`0x4f316f`): with `+0x3c5` set, it converts the stored J2000 coordinates to B1950 and **writes them back to the globals before the prefill**; ItemIndex := `+0x3c5`. Units: RA (h·15)·π/180 in, (α·180/π)/15 out; Dec °·π/180 in, δ·180/π out.
- `OKBtnClick`: after both validations `+0x3c5` := (ItemIndex = 1) (`0x4f36b0`); for B1950 the entry is converted to J2000 and stored. A validation error writes neither the flag nor the globals.
- The epoch radio has no handler: choosing an epoch converts nothing. Cancel (`bkCancel`) neither converts nor rolls back.
- Hot-list selection writes `+0x3c5` := 0 (`0x567bb1`) and disables the group: that dialog is fixed J2000, and an earlier B1950 choice is forgotten. Closing the list without a selection keeps it.
- The slew confirmation reads the flag at `0x566dc7` (non-transit) **and** `0x566f1b` (transit); each appends pchar `0x5672f8` before the Yes/No box at `0x566f43`.

**Original quirks kept.**
- **Southern cap sign loss:** an entry with Dec at or below about −89.427° (threshold rounded for display; the branch is decided in radians: within 0.01 rad of the south pole) becomes a northern Declination. The dialog warns (polite status region) while the current entry would do this at OK, and the confirmation says so. The same branch applies to the converting reopen: when an open converts a stored southern Dec inside the cap, the B1950 target it stores is northern. A separate dialog warning (`antenna-b1950-reopen-pole`) says so for that open: it is web-only dialog metadata (`openSouthPoleSignLost`), not native or persisted state, kept through edits, epoch choices, error boxes and route re-presentation (the stored target stays northern until a valid OK), and absent after the next open, OK, Cancel or hot-list selection. It describes the stored target only; OK uses the fields and epoch then entered.
- **Converting reopen:** after a B1950 OK, every Set Coordinates converts the stored target to B1950 and stores those values. The fields show them rounded (RA to 0.01 s, Dec to 0.1″; rounding is applied before OK reads the fields, and near the poles the original conversion cannot be undone exactly), and the negative-subdegree prefill quirk can drop a minus. With B1950 chosen, a valid OK converts the fields to J2000, which can change the target; with J2000 chosen, it stores the fields directly without conversion. Cancel leaves the B1950 values stored, and the next open converts them again as if they were J2000 (drift of about 50 years of precession per cycle). The dialog, the stored-coordinates label and the Cancel status say this. A lost-minus note suggesting `-0` in the degrees field is shown while the stored B1950 Dec is below 0 and the **current** Declination fields, read with OK's own exact parse, minus test and admission, give a positive Dec with a zero degree written without `-` (`skyCoordsPrefillMinusLost`). Components whose sum is not positive (a negative Dec, or arcminutes/arcseconds cancelling exactly to zero), a prefill carried to −1°, a prefill rounded to 0/0/0.0, an explicit `-0` and invalid text give no note; negative arcminute/arcsecond components whose admitted sum is still positive (for example `0`/`-30`/`3600` or `0`/`31`/`-60`) do show it. The parser is not changed or repaired.

**Browser policies** (provenance WEB-EP-01…04):
- **WEB-EP-01:** the activation runs once per explicit open. Route Back/Forward, error boxes, page dialogs and project operations re-present the draft without converting again.
- **WEB-EP-02:** radio-local; the native sharing with `TObsrvtry` (`0x539bff`, non-canonical dossier) is not ported.
- **WEB-EP-03:** the confirmation shows a short note labelled "OpenVireo note" (the original appends its own undecoded line `0x5672f8` there; that text is not reproduced). `openSouthPoleSignLost` (above) is web-only dialog metadata. `targetHoldsB1950` is web-only display metadata; `skyCoordsB1950` is the recovered flag. Neither is persisted.
- **WEB-EP-04:** binary64 in source order, constants rounded once, and an output-range invariant that throws (not a user gate).

**Numerics and limits.** The conversion is precession only: no proper motion, nutation, aberration or catalogue frame correction. There is no x87/Extended reproduction. binary64 rounding can choose the other Dec branch right at the 0.01 rad threshold, or 24 h instead of 0 h near zero; no certified bound against the original is available and no deadband is added.

The unit tests restate invariants (pole → 90° − |θ|, separation preserved outside the caps, threshold within two ulps of the exact source boundary). They also check the coordinator's synthetic V1–V3 display fields (`app-reference-vectors.json`, SHA-256 `f77b4c69…3862`; Decimal reference, not observations or a native oracle). The agreement observed in those tests (≤ 1e-11 h / 1e-10° on V1–V3) describes this policy on that sample only.

**Not ported:**
- the `0x5672f8` text;
- the meaning of record bytes +0/+1;
- native re-activation semantics;
- cross-lab sharing.

The `feature58` aggregate is not changed: receivers, the beam and the other I06 pieces remain gated.

## Manual N/S/E/W hold (RA-16…RA-18; RA-19 in "RA-19 keyboard table")

Evidence: the coordinator's entry-aligned listings and typed values in `/tmp/clea-static-research/radio-manual-slew-preparation/` (method entries authenticated by the `TRadioLab` metadata, REA section-header record `ev_e38712cf…`). The overall linear listing is misaligned near `0x565e58`, so those files are the authority. No new REA call and no runtime witness are claimed.

**Source facts.** `NBtnMouseDown` `0x5662a0`, `SBtnMouseDown` `0x5663c4`, `EBtnMouseDown` `0x5664e8` and `WBtnMouseDown` `0x566634` require the left button and a clear latch `+0x5d2`, write the direction and step, enable `SlewTimer` (`+0x448`, 100 ms) and set the latch; the other three buttons, RateSpin and Slew are disabled. The matching `MouseUp` handlers require the latch, the left button, `Width > X` and `Height > Y` (no lower bound, no check of which direction is held), disable the timer, clear the latch and enable RateSpin, the other buttons and Slew. E/W `MouseUp` then call `ClocktimerTimer` when Tracking is off (`0x566628`, `0x566778`). `SlewTimerTimer` `0x565e58..0x566210` steps Dec (N/S) or RA and HA (E/W), reflects at the pole (Singles 90, 0, ±180, 12; captions `'S'`/`'N'` at `0x566230`/`0x56623c`) and checks the proposal with the altitude predicate, which returns True at once with limits off (`0x5668f9`). On True it writes the result; on False it takes the failure path (RA-12). The first `FormActivate` clears the pole flag (`0x5649e7`). `DriveBtnClick` returns at once while the latch is set.

**Implemented** (`src/core/radioAntenna.ts`): `pressManualSlew`, `manualSlewTick`, `releaseManualSlew(state, options, clock|null, 'release'|'cancel')`, `manualButtonEnabled`, `manualButtonCaption`, `radioLabManualRefusal`, `radioLabManualTickRefusal`; state fields `poleReversed` (`+0x5d4`) and `manualRun` (browser token). `manualPress` stands for both the latch and `SlewTimer.Enabled`, which every recovered writer changes together. The panel shows a cross-shaped pad in the Drive section (DOM order N, S, E, W; E/W only when visible), the held direction in Motion, a pole note, the reason the buttons are unavailable and the last cancellation cause.

**Browser adaptations** (`docs/RADIO-ANTENNA-PROVENANCE.json` WEB-MANUAL-01…04):
- **Ownership and cancellation (WEB-MANUAL-01, `src/core/radioManualInput.ts`).** One owner per hold: the first admitted pointer whose `pointerdown` on the button reports button 0 (left mouse button, a touch contact or a pen contact) while no owner exists, captured so its release anywhere ends the hold; or Space/Enter on the focused button. `PointerEvent.isPrimary` is not checked, so a second finger can start a hold when the first finger is not holding one. While an owner exists a second finger, other buttons, auto-repeat and other keys are ignored. A `pointermove` from the owner reporting button 0 with bit 0 clear in `buttons` (left released while another mouse button stays down, reported by Pointer Events as a chorded `pointermove`) releases like `pointerup`. Limit: a left press while another mouse button is already down arrives as `pointermove` and starts no hold. Window blur, a hidden page, leaving the route, a project operation, any modal (ours or a page `<dialog>`), closing the panel window, unmount, pointer cancel and focus loss of a key owner cancel the hold. It never resumes; a fresh press is needed. Natively a release beyond the right/bottom edge keeps the hold and deactivation leaves the latch set.
- **Keyboard (WEB-MANUAL-02).** The buttons are focusable (native TabStop False) and at least 44 px; Space/Enter on the focused button hold it. The native letter/numeric-keypad table (RA-19) is mapped in part under WEB-KEY-02/03 (see "RA-19 keyboard table"). A click alone does nothing.
- **Step domain (WEB-MANUAL-03).** N/S |step| ≤ 180°, E/W |step| < 24 h, both finite and advancing; otherwise the press or tick is refused without change.
- **Programmed-slew interlock (WEB-MANUAL-04).** Natively a press during a programmed slew is reachable (Tracking off then on) and overwrites the shared `+0x53d`/`+0x525`; the browser refuses it. This is not a claimed native rejection.
- **Clock.** During a hold the clock tick takes its copy branch (RA held, HA := LST − RA). The E/W release with Tracking off chains the clock tick only with a valid supplied reading; without one the release still happens and RA/HA are kept (WEB-CLOCK-01, WEB-HA-01). Release and cancellation are never blocked by unsupported options, limits, a bad step or an unknown HA.
- **Limits.** With Limit Slewing on, a press or tick needs an accepted clock reading and a known HA (`manual-limits-clock`, WEB-ALT-03). Each tick checks its proposal (RA-12). A tick whose verdict the browser cannot decide is refused and suspends the hold (`manual-altitude-undecided`). Options outside WEB-OPT-01: refused, and a hold whose options change mid-way is suspended (Motion says why) until released.

**Not modelled:** the pole call `0x408c44` (import unresolved, probably a sound), LEDs, beam `0x561e88`, the original limit-failure literals (OpenVireo wording is shown), native capture semantics and Windows timer cadence. **Numerics:** binary64 in source order; Extended K rounded once; no x87 emulation. Near |Dec| = 90 or Dec = 0 a binary64 sum may decide differently from Extended; no tolerance is added and no error bound is claimed. Unit and browser tests restate the operations independently; they are not native oracles.

**Browser coverage and limits (`tests/radio-manual-app.spec.ts`).** Actual App paths cover the chorded left release, leaving the route (Back), closing the panel window, a real lost pointer capture and the E release with Tracking off while the radio clock runs. Not covered by an App path: pen input; unmount (the route stays mounted); the E/W release with an unknown HA (no admitted App path: compiled options have no instant slew). The touch test uses CDP `Input.dispatchTouchEvent` calibrated to one Chromium version: a non-empty `touchEnd` ending only the listed contact was observed there, while the installed protocol comment documents `TouchEnd` without touch points, so it is not a cross-version or native-input claim. Whether a secondary touch synthesizes a click is recorded per run.

## RA-19 keyboard table

## Altitude limit (RA-12)

Evidence is in `/tmp/clea-static-research/radio-ra12-altitude-20261023/`:

- the RTL stubs `0x4036ac`/`0x4036bc`/`0x426ff4`;

**Source facts.** The predicate receives Self (`TRadioLab`) in eax and two Extended stack arguments: the first pushed is the **hour angle in hours**, the last pushed is the **Dec in degrees**. It runs these steps:

1. If byte env+0x37cf (record+0x93a, "Limit Slewing") is 0, it returns True at once.
2. h := HA × 2π / 24 and d := Dec × π/180, where 2π is Extended `0x566a1c`, 24 is Single `0x566a28` = 24.0 and π/180 is Extended `0x566a2c`.
3. x := sin(lat)·sin(d) + cos(lat)·(cos(h)·cos(d)), with lat the Extended latitude env+0x3793.
4. alt := ArcSin(x) = atan2(x, √(1−x²)). This RTL routine has no domain guard.
5. It returns False when the threshold env+0x37a1 (record+0x90c, radians) is ≥ alt. Equality fails.
6. Otherwise it returns True only if |Self+0x5e9| ≤ Single `0x566a38` = 90. Self+0x5e9 is the stored current Dec, not the argument.

## Numeric admission of coordinate entry (web domain, not original behavior)

The original `OKBtnClick` computes RA = (h + m/60) + s/3600 and Dec = (d + m·sign/60) + s·sign/3600 in x87 Extended, then checks only the final sums against [0, 24] and [−90, 90]. Native accepts signed and noncanonical components (for example 25 h −60 min, or 5° 90′) and has no limit on any single field. This port keeps that: there are no per-field ranges, RA is checked before Dec, and the Dec sign rule is unchanged (Sign(d), or −1 when d is exactly zero and its text contains `-`, read through `Pos` at `0x40640c`).

The earlier candidate added the parsed binary64 fields in the native order. An independent check showed what that does with large components. The entry 9007199254740993 h, −540431955284459520 min, 3600 s is exactly 2 h, but it was admitted as 1 h. The same entry with −540431955284459580 min and 0 s is exactly 0 h, but it was rejected as a range error. And `24.000000000000001` h was admitted as 24. The earlier formula also rejects 0.7 h −41 min −60 s, which is exactly 0 h. No blanket disclaimer makes hour-scale errors acceptable, so the browser now uses this explicit domain (`SKY_COORDS_WEB_DOMAIN`, `admitCoordinate`):

1. **Exact value.** Each field that passes the strict grammar is read as an exact decimal. R = a + sign·(b/60 + c/3600) is formed as an exact rational, and S = |a| + |b|/60 + |c|/3600.
2. **Error bound.** Each term of the formula passes through at most four roundings: parse, divide and two additions. So any evaluation that rounds each of them to 53 or more bits stays within γ₄·S < E = 2⁻⁵⁰·S of R. Binary64 does this, and so does Extended if its `StrToFloat` is faithful; that is an assumption, not verified.
3. **Range error (original box).** If R is outside the range by more than E, the original error box appears (`ra-invalid`/`dec-invalid`). Every such evaluation would agree, so this is the native range check, not a guess.
4. **Cancellation (browser box).** Otherwise, if S > 10⁶ (hours for RA, degrees for Dec), the entry is refused as `ra-unsupported`/`dec-unsupported` with reason `cancellation`. Large components that cancel are where finite-precision results become hour-scale wrong, so the browser does not pick one result.
5. **Precision (browser box).** Otherwise, if R is outside the range by at most E, the entry is refused with reason `precision`. It sits closer to the bound than finite arithmetic can resolve: native would probably round it onto the bound and accept it, while exact algebra says it is out of range. Neither verdict is claimed.
6. **Accepted.** Otherwise R is in range and is stored as the nearest binary64 (ties to even). The bounds 0, ±90 and 24 are representable and rounding is monotone, so the stored value is finite and never moved across a bound. Nothing is clamped.

**Why material cancellation is ruled out.** Inside the domain S ≤ 10⁶, so E ≤ 2⁻⁵⁰·10⁶ ≈ 8.9·10⁻¹⁰ of the unit. That is 3.2 µs of time or 4.8·10⁻⁵″ for RA, and 3.2·10⁻⁶″ for Dec. Any faithful evaluation of the original formula agrees with the exact value to within this bound. That is far below the dialog resolution (0.01 s, 0.1″) and the ≈10⁻⁵ h arrival tolerance. Ordinary sexagesimal, signed and noncanonical entries have S of a few hundred at most.

**Remaining conversion error.** The stored value is within half an ulp of the exact value: at most 1.8·10⁻¹⁵ h for RA and 7.1·10⁻¹⁵° for Dec. Compared with the earlier binary64 accumulation it differs by at most E (generated checks in `radioAntenna.test.ts`).

**How it differs from native admission.**
- The browser refuses entries the original program evaluates: S > 10⁶ with cancellation, and entries outside the range by less than E.
- The browser accepts every exactly in-range entry. The original program might reject one when its own rounding lands just outside a bound; for example, it might reject 0.7 h −41 min −60 s.
- Native x87 results are not reproduced, and no parity is claimed. The refusal is a browser message box (`antenna.notice.webDomain`), not an original message.
- As with every OK error, the draft fields, the open dialog, the stored target and the pointing do not change.

## Held keys in the dialog and message boxes (browser policy)

Before this correction, holding Enter in a coordinate field cascaded through several steps by key auto-repeat: OK, then Yes on the confirmation (the slew started), then Set Coordinates on the restored focus (the stop question), then Yes (stopped), then the dialog reopened. Holding Escape on an error box closed the box and then cancelled the dialog, discarding the edits. Both were reproduced with Playwright on the unchanged panel; the failing baseline report is in the correction evidence folder. The panel now ignores auto-repeated Enter/Escape (`KeyboardEvent.repeat`) inside the dialog and the message boxes, so only a fresh key press acts there. This is a browser input policy, not recovered behavior: how the original Windows dialogs treat key repeat is not established.

RA-12 is the first path that opens a box during a key-owned hold. Reproduced in Chromium before the fix: a Space hold on a direction button failed at the horizon limit, the box's OK took focus, the next auto-repeated Space keydown armed OK and releasing Space dismissed the box. Message boxes now also ignore auto-repeated Space keydowns, so a fresh Space press still answers the focused button. The shared Enter/Escape guard is not widened to Space, because it also covers the dialog's text fields, where holding Space is ordinary typing. This is a synthetic browser witness, not a native Windows or physical-device one.

`answerNotice(state, options, kind, answer)` refuses an answer meant for a box of another kind. It does not tell apart two successive boxes of the same kind. The panel always passes the kind of the box it renders, and a stale click cannot reach an unmounted box, so no same-kind late answer was found apart from the held-key cascade.

## Browser timer ownership and option profile

These are explicit web policies, not recovered Windows timing or native options validation. `radioTimer.ts` owns a periodic registration, reads the latest committed input on delivery, suppresses duplicate delivery from the same uncommitted input, and ignores callbacks after cancellation. Tracking/rate changes do not restart its cadence. Pause, completion, unmount, unsupported host options, or a Dec→RA switch callback that would take its RA step from an unsupported stored rate (`radioLabTickRefusal`, see below) end the registration; hiding the panel leaves it running. Motion then names which of the two browser limits suspended the slew. The component additionally checks the latest enabled/run ownership before handling a callback, including the gap between a React commit and passive-effect cleanup, so an ending timer cannot overwrite its completion result. Browser scheduling can coalesce deliveries; this is not one guaranteed native tick per elapsed 100 ms.

The panel's SlewTimer2 and clocktimer callbacks and its antenna user actions all step from the latest accepted antenna state. Each accepted transition writes it synchronously before it is handed to the host, and a new host `antenna` prop (by identity) replaces it; other commits keep it. So a slew and a clock callback that run in the same task before React commits chain in either order instead of the second overwriting the first (reproduced with a test-only interval wrapper, synthetic scheduling; not a Windows or Chrome throttling witness). The run, registration, modality, notice-kind and busy guards are unchanged; stepping and numerics are untouched.

`radioLabProfileIssues` separately checks a shape-valid host option record: initial latitude must produce finite Dec within [-90, 90] degrees, and reachable rate indices 1 through max(4, configured maximum) must yield finite positive advancing Dec/RA steps with RA step < 6 hours. The browser refuses unsupported options without clamping or replacing state. A changed unsupported profile suspends motion; restoring a supported profile resumes it. Under unsupported options, Tracking, the Slew Rate buttons, opening the coordinate dialog, its OK and the confirmation's Yes are refused. An open coordinate dialog can still be cancelled, and a running slew can still be stopped through Slew ▸ Set Coordinates… only while that menu item is enabled: on a non-transit telescope it is disabled while Tracking is off, and Tracking cannot be turned on until supported options return, so Stop is unreachable in that state. The original INI/dialog validation and current classroom options are not established. These controls do not authorize acquisitions or supply the observation clock.

The option record alone does not cover the panel state. After the first FormActivate (index 4, rate computed from the options then current), the original recomputes the rate only in RateSpin and in the start loop, and the start loop only raises the index to the options maximum. So an index set under earlier options can be kept above max(4, maximum). Example: options A (maximum 6, base 50) are switched to B (maximum 4, base 3241), and RateDown then gives index 5 with rate 324100, an RA step of about 6.002 h.

A rate is checked only where a step that moves the telescope comes from it, with the live options deciding the branch and the coordinates deciding whether an RA step is taken. The native consumers, from the derived listings behind RA-10/RA-11, are:

- The start loop (0x566f6b) raises the index to the options maximum when it is lower and writes the rate and the Dec step from it (0x566f8a). This runs before the instantSlew branch too, so an instant start can recompute and store the index, the rate and the step although none of them moves the pointing.
- The callback reads the stored rate once, at the Dec→RA switch of a non-transit telescope (0x5674ff..0x56750f): d = target RA − pointing RA (negated when |d| > 12 h), +0x53e := Extended 0x5678d0 (≈1e−5 h) ≥ |d|, step := Sign(d) × rate × ≈1/3600 / 15. When +0x53e is set, the same callback completes: the RA step is stored in +0x525 but never added, and RA is not snapped.
- The Dec and RA phases add the fixed step +0x525.
- A transit telescope goes from Dec straight to phase 3.
- instantSlew writes the pointing at once (0x566fb3).

The tolerance, the arithmetic and its order are the existing ones (`slewTimerTick` and the gates share `raSwitchSeparation`/`raSwitchFinishes`); nothing is snapped, clamped or added. The Dec phase does not change RA in this slice (a manual press during a slew is refused, WEB-MANUAL-04, and a clock tick during a slew only copies the HA), so the separation at the switch is the one between the current pointing and the target, re-evaluated from the latest state.

`radioLabRateIssues(state, options)` therefore reports:

- `stored`: during the Dec phase of a non-transit slew whose switch takes the RA step (|d| above the tolerance), the rate that step is computed from. Dec callbacks keep running. Only the switch callback is refused with `rate-unsupported` (`radioLabTickRefusal`), and from then on the panel registers no interval. The RA phase, transit slews and switches within the tolerance never add a step from the stored rate, so nothing is reported or suspended there. The host may switch the transit option between phases; the switch decides from the options live when it runs.
- `start`: the rate after the start loop, for the coordinates the next start would use: inside the open dialog, the draft when it is a valid J2000 entry whose OK reaches the confirmation; in the slew confirmation (or the transit note before it), the committed target; otherwise no coordinates are chosen yet, and the note says which coordinates it covers. With instantSlew nothing is checked. On a transit telescope, or when the switch would finish within the tolerance (for example a Declination-only slew), only the Dec step is checked (finite, positive, changing every in-range Dec). Otherwise the full criteria apply, because the same rate gives the RA step at the switch. OK and Yes are refused for those coordinates, and each is checked against the options live at that answer.
- `down`/`up`: a RateSpin press during that same Dec phase, which would store the rate the switch takes its RA step from. That press is refused. These are not listed while a dialog or box is open, because every press returns `modal-open` there.

OK keeps the original order for everything that never starts motion: the option-record check (`radioLabProfileIssues`) still comes before parsing, as before, but the state-context rate check now follows the parse and web-domain results and uses the converted J2000 target for a B1950.0 draft (RA-EP-03; superseding the former B1950 gate). Invalid text gets its own error or browser box, an entry equal to the pointing stores the coordinates and gives the no-slew warning. With limits enabled on a non-transit telescope, the coordinates are stored first and then `limits-require-clock` is reported when no request-time reading is supplied; with a reading, an altitude failure or an undecided verdict shows its box and stops (RA-12). Only an OK that is on the path to a possible start with an unsupported rate for its coordinates is refused, and then nothing is stored: the draft, the stored target and the pointing are kept. That rate check (`okReachesConfirmation` and `startIssueFor`) runs before the coordinates are stored and the dialog closes, so with limits on it applies only after an altitude pass: a pass whose start rate is unsupported refuses OK before storing and keeps the dialog, while the clock gate, a failure and an undecided verdict still store first. On a transit telescope the rate gate comes before the transit note, and the altitude check runs at the note's OK. "On the path to a possible start" means that OK would go on to the slew confirmation, or, on a transit telescope, first to the transit note whose OK leads to that confirmation; the gate applies before the transit note, not only immediately before the confirmation.

RateSpin presses in the RA phase, on a transit slew, before a switch within the tolerance, and without a slew keep the native arithmetic and are applied. This lets the user step through an unsupported index to a supported one, so a kept or restored rate stays recoverable through the next start's gate. Recovery from a halted switch: stop the slew with Slew ▸ Set Coordinates… while that menu item is enabled, press to a supported rate while the Slew Rate buttons are enabled, or have the host turn the transit option on. Inside the coordinate dialog or a message box the reason says to close it first (Cancel on the dialog, No on the confirmation, Cancel on the transit note, or OK on any other box), because the Slew Rate and Tracking buttons behind it return `modal-open`. The transit note is named separately: its OK does not release the buttons but opens the slew confirmation.

The RA tolerance compares the plain hour values. There is no circular wrap: a pointing at 0 h and a target at 24 h are 24 h apart for this check (|d| > 12 h only negates d), so such a slew takes the RA step from the rate. The notes say so in their wording; the arithmetic is unchanged.

Constraints that remain:

- `trackingVisible` is set at the first FormActivate from the transit option then current and never changes, so a panel that first initialized as a transit telescope has no Tracking button whatever the live options are. Its Slew Rate buttons stay disabled until a programmed slew ends or is stopped. Until then a refused start can proceed under options whose maximum exceeds the kept index (the start loop then recomputes the rate) or with instantSlew; when only the RA step fails under live non-transit options, also with the transit option on again or with coordinates within the tolerance of the pointing RA. Under the web profile no supported record has a maximum above 8, so for a kept index of 8 or more the maximum route is unavailable: the panel then leaves that alternative out and says that raising the options maximum cannot help (it checks the most permissive record, rate base 1, at maximum index + 1 with `isSupportedRadioLabProfile`; presentation only).
- The fixed step +0x525 is not re-checked for a host-supplied state. Review finding 2 (conditional, from source reading) noted that a synthetic `patchAntenna` state with a malformed rate and a zero or negative step, which the earlier rate guard happened to stop, now runs its Dec callbacks without progress or away from the target. No supported UI, import or restoration path producing such a state was demonstrated, so no native step validation is invented; callers that restore antenna state are assumed to supply a step written by `startSlew`.

The panel shows a slew-rate limit note and marks a suspended slew in Motion, naming the cause. When OK or Yes is refused, the open dialog or confirmation box lists the reason for the coordinates it would use. Nothing is clamped or recomputed. These are web policies, not native validation. The whole-option-record profile (`radioLabProfileIssues`) stays a conservative web policy, unchanged by this gate.

Independent Chromium controls did not reproduce the review's suggested Enter cascade after arrival: actual focus was BODY, and held Enter did not change Tracking or the radio switch. That hypothesis is not a confirmed fixed defect; regressions preserve the observed behavior without forcing a new focus target.
