# Observation notebook deletion and recovery

Observation results now supports explicit **Delete observation result N**, a confirmation review and **Undo last observation deletion**. Undo restores the exact prior notebook, including type codes, literal remarks/spaces, source identities, stable surviving/deleted row IDs, row order and reuse/append mode. The separate recovery copy survives reloading when browser storage works and can be exported as an ordinary notebook-v1 file. No spectral label is reparsed to undo.

This is a bounded **web safety adaptation** grounded in recovered native confirmation/one-record backup/Undo behavior. It does not claim native list-pointer/order/runtime equivalence, general edit undo, a multi-level history or native `.DAT` compatibility. Native numerical fields remain unavailable; none are invented.

## Try locally

1. Open `http://127.0.0.1:5173/#classification`. Select an original **Practice object** and confirm a notebook observation. The browser status must report saved. Existing manual answers and classification/width histories remain separate.
2. Click **Delete observation result N** for that practice. Review its object/type/code/remarks/source SHA. Focus starts on **Cancel deletion action**. Cancel or Escape keeps both the notebook and recovery storage unchanged. Source/file/navigation activity cancels an obsolete review; closed/stale/double confirmations cannot apply it again.
3. Confirm **Delete confirmed observation**. One row disappears; stable remaining row IDs are not renumbered. A full before/after recovery is staged before the main browser copy is changed. If that staging or a comparison/write check fails, the operation reports failure and keeps this view;a staged recovery can remain and should be inspected after reload.
4. Reload. **Undo last observation deletion** restores the exact previous notebook when the active notebook and browser copy match the deletion's after-state. It also clears recovery after saving the restored notebook. If cleanup fails, the restored notebook remains saved and recovery is retained for explicit cleanup.
5. **Export deletion recovery** downloads the complete prior notebook in the unchanged notebook-v1 format. **Export observation notebook** still exports only current rows: it does not embed the pending recovery. Keep both exports if you need both states on another browser/origin.
6. To keep the deletion, choose **Review finishing deletion**. Cancel/Escape keeps recovery. **Finish deletion recovery** explicitly discards only the recovery copy, keeps the current notebook and enables editing again. Export recovery first if you want to retain it. Finishing recovery has no undo.

Only one recovery is pending at a time. While it exists, new observations, row edits, another deletion, reuse/append changes and standalone notebook restore are paused. Export/current legacy investigation workflows remain available. Resolve recovery by Undo or explicit Finish before further notebook mutations. This avoids overwriting a previous backup or colliding IDs, and makes exact whole-notebook Undo safe. After an explicitly finalized last-row deletion, a later new row can reuse the now-vacant terminal ID;IDs are local row identities,not global immutable identifiers.

## Storage/error policy

The main key `openvireo.observation-notebook.v1` and all exported notebook-v1, historical investigation/classification JSON and CSV remain unchanged. Recovery uses a **separate** `openvireo.observation-deletion-recovery.v1` key with strict local envelope: format `OpenVireo observation deletion recovery`,version1,recordId,before,after. Both embedded values must be valid notebook-v1 envelopes,and after must be precisely before minus that one ID with the same mode and unchanged remaining rows. Maximum recovery size is two128KiB notebook limits plus4096bytes. Corrupt/oversized recovery is preserved as exact text and exportable,never interpreted as permission to delete data.

The write protocol compares current main/recovery keys,stages a complete validated recovery,checks both keys again,then writes the after-state. Undo compares both keys,saves the full prior notebook first,checks again and only then removes recovery. Finish compares both reviewed keys and removes only recovery. These are ordered safeguards,not an atomic two-key localStorage transaction. Perfectly overlapping older clients,blocked reads after a write and clearing browser data remain limitations. Never automatically retry an uncertain write: export both available copies,then reload to inspect actual state.

If the notebook already equals the before-state,an interrupted stage or cleanup left a harmless extra recovery:Undo is disabled because its records are already present. Explicit Finish removes only that extra copy. If notebook and recovery describe different states,no automatic merge or overwrite occurs:export both,reload and intentionally choose what to restore. Other-tab events stop automatic saving and retain an already known recovery in memory even when another tab removes or changes its key,so it remains exportable until reload. A corrupt or absent main copy can be repaired by exporting recovery,explicitly finishing its separate copy,then restoring that exported valid notebook. Storage-denied/quota cases pause destructive operations rather than pretending a recoverable deletion was saved.

Browser copies remain origin-scoped convenience storage;export backups before clearing/private/address changes. No server,network transmission,encryption or secret-storage feature. Earlier memory-only notebook rows absent from files/browser storage cannot be reconstructed.

## Native evidence and boundary

[Hashed provenance](OBSERVATION-DELETE-PROVENANCE.json) binds the correct method-table entries `DeleteSelectedLine1Click`→0x54978c and `UndoEditDelete1Click`→0x54993c to the preserved executable SHA256 `781bc9704b4674038267834a9ed21d502c455378d8fc9eb15a1653e20c52c54c`. Other forms contain the same method names at different addresses;they are excluded.

Native deletion `[0x54978c,0x5498d5)` initially disables Undo/clears+3ec,requires a selected non-header row,asks confirmation and returns on result7. It retains the selected display index/string,looks up data index-1,copies0x24DWORDs(144bytes)to+3f0,removes the current data/display row,sets+3ec=1 and enables Undo. Native Undo `[0x54993c,0x549a27)` selects the delete/add-back or edit/copy-back branch by+3ec,reconstructs/inserts/replaces the display row and disables Undo. This is one retained record,not an undo stack.

The data-list add helper and displayed-row insertion are distinct;the web restores its own exact prior ordered snapshot and does not infer identical native ordering. Unlike the native early disable,the web keeps existing recovery when a review is cancelled and requires explicit Finish before discarding it. Only deletion Undo is ported here;general native edit Undo and complete list/callback/runtime behavior remain open. Static code and chosen tests are not original execution or a scientific/grade/FPU/pixel oracle. Original resources/hashes,integrator,sampler,source+skySUM,acquisition/counts/seed,manual answers,legacy confirmed histories and grades remain unchanged. All64primary statuses unchanged;project partial. External review remains pending human authorization with0new attempts,no substitute,push or deployment.

Selected-row edit Undo is now supported separately;see [scope and shared recovery compatibility](OBSERVATION-EDIT-UNDO.md). Existing deletion-v1,notebook-v1 and deletion behavior remain unchanged. The same historical recovery key accepts a distinct strict edit-v1 profile;unknown/unreadable recovery uses generic export/Finish labels. Resolve either operation before another notebook mutation. This does not expand native numerical metadata or DAT authority.
