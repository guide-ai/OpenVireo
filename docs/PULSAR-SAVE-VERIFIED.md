# Save capture with verification (R-RX15, analysis only)

Pulsar Analysis can save the receiver recording held in this tab to **one file the learner chooses in the browser**, and mark it as written only after the copy has been read back equal. The button is **Save capture as .PLR (verified)…**, shown only for memory data, next to the R-RX14 **Download capture as .PLR…**.

This is a **web Save**, not the original Save dialog:

- The bytes are the R-RX14 canonical `.PLR` bytes of the capture ([PULSAR-RAW-EXPORT.md](PULSAR-RAW-EXPORT.md)), with the same refusals, rounding list and model-origin warning. The data is **model-generated by the receiver simulation, not observed CLEA data**.
- The receipt is the web counterpart of the recovered `+0x97 := 1` and `+0x9a := name`. It is **historical**: a check of that file at that moment, for that data version. OpenVireo does not watch the file afterwards; a later save to the same file, or another program, may change it.
- At R-RX15 the three original Save-Yes paths (receiver finish question, arming unsaved prompt, analysis Load prompt) stayed **gated**, with reasons pointing to this dialog. Since R-RX16 the arming unsaved prompt's Yes opens a separate Radio-owned dialog that reuses this Save's code and receipt unchanged ([RADIO-RECORD-SAVE.md](RADIO-RECORD-SAVE.md)). Since R-RX17 the receiver finish question's Yes opens another Radio-owned dialog, which records the same kind of receipt through a separate owner-aware recorder ([RADIO-FINISH-SAVE.md](RADIO-FINISH-SAVE.md)). Since R-RX18 the analysis Load prompt's Yes opens this same Save dialog for its flow, and only that flow's own verified receipt leads to a separate, fresh Load choice ([PULSAR-LOAD-SAVE.md](PULSAR-LOAD-SAVE.md)). Radio is not complete, and no native Save equivalence is claimed.

No CLEA execution, emulation, native dialog or native trace was used, and no original file written by the program is available. The tests check this implementation's contract, not the original's behaviour. Runtime FPU, RNG, GDI, locale and durability limits of the earlier increments are unchanged.

Binary `CLEA_VEO.exe` SHA-256 `781bc9704b4674038267834a9ed21d502c455378d8fc9eb15a1653e20c52c54c`; baseline commit `2ca5fb387e0e3d22957d6804ac2940425fc31d6e`. Tags: [S] static listing (preserved bounded static REA/GNU objdump evidence, no fresh REA provider run), [I] analyst inference, [W] web policy. Listings, hashes and evidence files are in [PULSAR-SAVE-VERIFIED-PROVENANCE.json](PULSAR-SAVE-VERIFIED-PROVENANCE.json).

## Modules

- `src/core/pulsarCurrentData.ts`: the owned write claim, the receipt (`written`), `recordPulsarWrittenCopy`, `pulsarWrittenCopy`, `pulsarCurrentSaved`, the name rule and the Properties text. Since R-RX16 also the shared output claim (`output`, `claimPulsarOutput`, `releasePulsarOutput`). Pure.
- `src/core/pulsarSavedCopy.ts`: support predicate, picker options, extension rule, `pulsarSaveBegin` (R-RX14 request order plus the claim), notices. Since R-RX16 also `PULSAR_SAVE_READBACK_MAX_BYTES`, the read-back bound for Save owners that must not import the PLR reader (the Radio arming Save); it is the strict reader's `PLR_MAX_BYTES` itself, not a separate number. Pure.
- `src/core/pulsarRawExport.ts`: the session gains `purpose` (`'download' | 'save'`) and a `save` notice. Byte builder unchanged.
- `src/components/pulsarSaveHost.ts`: browser I/O (feature detection, synchronous picker call, writable stream, close, bounded read-back, liveness). No React.
- `src/components/PulsarAnalysis.tsx`, `PulsarMessages.ts`, `PulsarAnalysis.css`, `RadioReceiverWindows.tsx`, `src/i18n/en.json`: wiring and text.
- `src/useSharedPulsarData.ts`: `update` is generic over step results, so the write step keeps its own refusal union.

## Web policy

- **WEB-SAVE-01 Support** [W]. Save is offered only in a secure context with a callable `window.showSaveFilePicker` and `FileSystemFileHandle.prototype.createWritable`, detected once per mount. Otherwise the button is disabled with a precise reason (`insecure-context` or `no-api`) and **Download capture as .PLR…** still works. No permission request, persisted handle, browser flag or setting is used. No backend, Worker or IndexedDB.
- **WEB-SAVE-02 Picker** [W]. The dialog shows, **before** the choice, that the browser asks for one file, that choosing an existing file can replace or empty it as soon as the choice is confirmed, even if saving then fails, is cancelled or the name is refused, and that OpenVireo cannot restore it. The click handler is synchronous up to `showSaveFilePicker(PULSAR_SAVE_PICKER_OPTIONS)` (no await before it, so the click's user activation applies). Options: `suggestedName: openvireo-model-capture.PLR`, one `.PLR` type; no `id` and no `startIn`, so no directory is remembered or suggested. There is no automatic research/resource path, no directory enumeration and no handle reuse. A rejection is reported once (`AbortError` → cancelled, anything else or a synchronous throw → refused) and never retried. No chooser overwrite confirmation is promised.
- **WEB-SAVE-03 Request and claim** [W]. Before the picker: the Download guards (session presented, active, no foreign modal, no output claim) and R-RX14's order `not-ready`, `stale`, a fresh build and its problem, preview equality (`rawExportRequest`). Then `pulsarWriteClaim` takes an **owned, immutable** claim in the same task: the producer-frozen data object (checked frozen), the generation, a frozen metadata snapshot, a frozen ordinary array copy of the samples (compared with `Object.is`, so `+0` and `−0` differ; non-finite samples refuse the claim) and the canonical ASCII text. Fresh bytes are made from that text for the write; the read-back is compared with the text. Claims are registered in a module-private `WeakSet`; a spread copy or hand-made object is not a claim.
- **WEB-SAVE-04 Extension** [W, from SAVE-EXTENSION]. A chosen name that does not end in `.plr` (ASCII case-insensitive) with at least one character before it is **not written by OpenVireo**: no writable is created. The non-empty stem is a [W] web policy, not a recovered native predicate: the name `.PLR` ends in `.PLR` but is refused, and the alert says that it is not a name ending in .PLR with at least one character before it. The dialog offers **Choose again…** (a new click and a new synchronous picker call, the counterpart of Yes 6) or Cancel. The native No 7 "write anyway" is **not offered** in this web subset: the picker may already have created or emptied that file, and the Load chooser accepts only `.PLR`. This is not an overwrite question.
- **WEB-SAVE-05 Write and receipt** [W]. `createWritable()`, one `write` of fresh bytes, `close()`, then `getFile()`; its `size` is bounded (2 MiB) **before** `arrayBuffer()`. `recordPulsarWrittenCopy` then refuses, in order: a claim it did not issue; a held capture lease; another data object or generation (`superseded`); the same object with changed metadata or samples (`source-mutated`); a read-back of another length or any different byte; a file name outside the web rule. On success only `written` changes: same data object, generation, lease, analysis activity, samples, cursors, zoom, measurement list and `listSaved`. R-RX17 note: `recordPulsarWrittenCopy` (and its lease refusal) is unchanged, and this dialog and the R-RX16 arming Save keep using it. The finish Save alone uses `pulsarFinishWriteClaim` / `recordPulsarFinishWrittenCopy`, a separate claim domain bound to the committed lease **object** and the radio output token; both recorders share the checks from `superseded` on and create the same receipt ([RADIO-FINISH-SAVE.md](RADIO-FINISH-SAVE.md), WEB-RX17-03). Origin stays memory, so `pulsarDataFileName` stays null and a measurement row keeps 11 columns with a blank File field. Receipts are frozen and registered in a private `WeakSet`; `pulsarWrittenCopy(doc)` returns one only while the data object, generation, metadata and samples still match.
  - File name rule [W, not recovered]: the browser basename (`FileSystemHandle.name`), 1..255 UTF-16 code units, no C0 control, DEL, `/` or `\`. It is refused, never cut. The 255 bound is a web policy; it is **not** an ANSI-byte equivalence with the cited `0xff` copy argument (`0x56a858`, SAVE-WRITTEN). No full native path is invented.
  - A refused commit after an equal read-back of data that changed meanwhile is reported as `verified-stale` (the file holds the data as it was when Save was pressed; the current data is not marked). Other refusals are `mismatch` or `file-name`.
- **WEB-SAVE-06 One claim, liveness, cleanup** [W]. The R-RX10 output claim (`exportBusy`) is held from before the picker call through write, close, read-back and cleanup; Download, Save, Cancel, Escape, Export and Append do nothing meanwhile, and the modal session keeps arming refused and newer-data adoption held. R-RX16 (WEB-RX16-05, [RADIO-RECORD-SAVE.md](RADIO-RECORD-SAVE.md)) adds a **shared** output claim on the App's current dataset document, `output = {owner, token}`:
  - This Save takes `('analysis', token)` after `pulsarSaveBegin` and before the picker. A synchronous picker failure releases it, and the attempt's `finally` releases exactly that owner and token after its cleanup.
  - The Radio arming Save takes `('radio', token)` the same way.
  - This dialog's Save and Download refuse (`not-ready`) while either owner holds it. This covers a Radio attempt whose route was hidden but whose stream is still being cleaned up, which `exportBusy` alone does not see.
  - A browser stage that never settles (most plainly a picker promise) therefore blocks across routes since R-RX16: the shared claim stays held until that provider promise settles, so a hung attempt of either owner refuses the other owner's Save (and this dialog's Download) with `not-ready`. Hiding the route marks the attempt abandoned but does not release the claim; the application forces no timeout or claim release while the promise is unsettled. A chooser Cancel that rejects the promise (`AbortError`) settles the attempt normally.
  - A dataset change keeps the claim. An older attempt never releases a newer one. Each attempt has a token; it is live only while the token is current and the panel is mounted and active. Liveness is checked after every await and before every new filesystem stage: a dead attempt creates no writable after the picker, aborts a stream that is open and not yet closing, and releases the claim only after that cleanup settled. Hiding the route or unmounting makes the attempt dead (the dialog shows `abandoned` when it reopens); a stale continuation never writes state. After `close()` began, the file may hold the new bytes: no rollback, deletion or repair is attempted or claimed. If `close()` rejects, OpenVireo makes one best-effort `abort()` of that stream on any path (live or abandoned) and waits for it to resolve or reject before it reports `close-failed` and releases the claim; a rejection of that abort is not reported over `close-failed` and is not retried. This only tries to settle the web stream: if the abort also rejects, OpenVireo does not claim that the browser released the stream, and in no case does it restore or roll back the destination or show anything about native or OS errors.
- **WEB-SAVE-07 Status and invalidation** [W].
  - Pending phases (`picking`, `writing`, `closing`, `reading`) are in a status region; failures are alerts. Every cancel, refusal, extension and failure text says what OpenVireo did not do **and** that the chosen file may already have been created, emptied or (partly) changed; none says "nothing written" or "unchanged" about the destination.
  - The memory panel shows "Last verified copy: {name}" with a note that it was checked when written and is not watched afterwards. Properties shows the basename only when the receipt belongs to the displayed current data object; older held data never shows it.
  - Every text that shows a chosen name (the panel status line, the dialog status and alerts, the last-copy line, Properties) wraps anywhere (`overflow-wrap:anywhere`); a name is never cut or hidden.
  - The receipt is dropped by every dataset change (import, arming erase, capture commit) and is never revived. A failed or abandoned attempt and a Download keep a valid receipt. A later verified save replaces it.
  - If another modal dialog (for example a host one) is open when an equal read-back is committed, the receipt is still recorded, but the Save dialog stays open with a `verified` notice. Its Cancel and Escape do nothing while the other modal is open. Afterwards they close it with a neutral text ("Save dialog closed. Closing the dialog does not change whether the recording is marked as written; …") that neither denies the new mark nor claims one.
- **WEB-SAVE-08 Saved flag and gated paths** [W]. `pulsarCurrentSaved(doc)` (an imported file, or a valid receipt) is `+0x97` for the arming snapshot (unsaved prompt skipped; erase prompt unchanged) and for the Load prompt (`pulsarRequestLoad(s, data, saved)`; omitted, the old value-only rule applies). The old `pulsarDataSaved(value)` is kept and deprecated. At R-RX15 all three Save-Yes buttons stayed disabled, with texts pointing to this dialog. Since R-RX16 the arming unsaved prompt's Yes opens the Radio Save dialog ([RADIO-RECORD-SAVE.md](RADIO-RECORD-SAVE.md)), whose receipt is this same `recordPulsarWrittenCopy` receipt. Since R-RX17 the finish question's Yes opens the finish Save dialog, whose receipt comes from the owner-aware `recordPulsarFinishWrittenCopy` ([RADIO-FINISH-SAVE.md](RADIO-FINISH-SAVE.md)). Since R-RX18 the Load prompt's Yes (enabled under WEB-SAVE-01 support, otherwise disabled with its reason) opens this dialog for a Load after Save flow; the saved flag is never that flow's load authority ([PULSAR-LOAD-SAVE.md](PULSAR-LOAD-SAVE.md)). An R-RX14 Download of unsaved data still leaves it unsaved; a Download after a verified save keeps the receipt. The imported file's exact-byte Download and the measurement CSV paths are untouched.

## Browser authority (primary sources)

- File System Access, `showSaveFilePicker`: <https://wicg.github.io/file-system-access/#api-showsavefilepicker>. One user-chosen handle; the picker may create or clear the chosen file before it resolves; requires user activation. A returned handle is not proof that the recording was written.
- File System Standard, `createWritable`: <https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable>, and `FileSystemWritableFileStream.write`: <https://fs.spec.whatwg.org/#api-filesystemwritablefilestream-write>. Writes are staged and become visible at `close()`; `getFile()` gives a fresh read-back. No physical durability guarantee.
- Chrome developer documentation: <https://developer.chrome.com/docs/capabilities/web-apis/file-system-access> (secure context and feature detection; picker from a user gesture).

The read-back comparison is an **OpenVireo policy** on top of these APIs. It is not native CLEA behaviour and not a hardware durability guarantee; no `fsync` is claimed.
